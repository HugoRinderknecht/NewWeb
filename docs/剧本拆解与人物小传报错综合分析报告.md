# 剧本拆解与人物小传报错综合分析报告

## 一、分析背景
用户反馈两个现象：

1. `剧本拆解` 页面已经能看到分集内容，但仍然报 `404`
2. `人物小传` 页面已经能看到人物小传内容，但仍然提示 `服务器内部错误`

本次分析基于以下信息综合得出：
- 前端运行日志：`C:\Users\MicaForever\Downloads\localhost-1780804131385.log`
- API 文档目录：`docs/API`
- 前端页面实现与统一数据层实现

---

## 二、结论总览
这两个问题都不是“主数据完全没拿到”，而是：

- **页面主体数据已经成功渲染**
- 但页面还会发起一些 **次级请求 / 详情请求 / 轮询请求**
- 这些请求失败后，被全局 HTTP 错误处理统一弹成了报错

因此当前问题的本质是：

> **主内容成功 + 次级请求失败 + 全局错误提示未区分关键请求与背景请求**

其中：

- `剧本拆解` 的核心问题更偏向 **后端数据一致性 / 详情接口查询逻辑问题**
- `人物小传` 的核心问题更偏向 **并行请求或轮询请求失败 + 前端错误提示过于激进**

---

## 三、问题一：剧本拆解已有内容，但仍报 404

### 3.1 现象复盘
日志中出现了明确的报错请求：

```text
GET /api/scripts/a32130b3-a28b-4e09-bc33-cd2bbebc1e60/episodes/0ebc9c8b2c1c17028f61db094c69fb3f 404
```

这说明报错的并不是剧本级分集列表接口，而是 **分集详情接口**。

也就是说，实际链路是：

1. 页面先请求剧本分集列表
2. 分集列表成功返回，所以页面上已经显示出“有内容”
3. 页面自动选中某个分集，或者用户点击某个分集
4. 触发“分集详情”查询
5. 详情接口 404
6. 全局 HTTP 错误处理弹出错误

---

### 3.2 对应前端代码链路

#### 分集详情接口定义
文件：`src/api/script.ts`

```ts
export function fetchGetEpisodeDetail(scriptId: string, episodeId: string) {
  return getApiAdapter().get<Api.Script.EpisodeDetail>(
    `/api/scripts/${scriptId}/episodes/${episodeId}`
  )
}
```

#### 分集详情 Query Hook
文件：`src/api/queries/script.ts`

```ts
export function useEpisodeDetail(
  scriptId: MaybeRefOrGetter<string | undefined>,
  episodeId: MaybeRefOrGetter<string | undefined>
) {
  return useQuery({
    queryKey: [QUERY_KEY, 'episode', scriptId, episodeId] as const,
    queryFn: async () => {
      const sid = toValue(scriptId)
      const eid = toValue(episodeId)
      if (!sid || !eid) return null
      return await fetchGetEpisodeDetail(sid, eid)
    },
    enabled: () => !!toValue(scriptId) && !!toValue(episodeId),
    staleTime: 60 * 1000
  })
}
```

#### 页面中先显示列表，再触发详情
文件：`src/views/script/decompose/index.vue`

页面会：
- 调用 `fetchGetScriptEpisodes(projectId, scriptId)` 获取列表
- 把列表结果直接映射到 `episodeList`
- 默认选中第一条
- 选中后由 `useEpisodeDetail` 去查详情

这意味着：

- 左侧列表使用的是“列表接口返回的数据”
- 右侧编辑区又会额外请求一次“详情接口”
- 如果详情查不到，就会产生“明明看到了内容但仍然报 404”的现象

---

### 3.3 根因判断
这个问题已经不能再简单归结为“无数据返回 404”。

因为现在的实际现象是：
- 列表能查到
- 详情查不到

所以更准确的根因是以下几类之一：

#### 情况 A：列表与详情的数据源不一致
后端列表接口能返回某条分集记录，但详情接口查询时使用的是另一套表、另一种过滤条件或另一种关联逻辑，导致同一个 `episodeId` 无法被详情接口查到。

#### 情况 B：返回了已失效/已删除的 episodeId
列表里带出了某条旧的、脏的、逻辑删除的、历史残留的 `episodeId`，详情接口严格按主键查询时返回 404。

#### 情况 C：列表接口返回的是聚合结果，详情接口返回的是实体结果
也就是列表层把数据拼出来了，但详情接口要求实体真实存在；如果实体被迁移、归档、软删除，列表仍可能显示，详情却失败。

#### 情况 D：前后端字段映射或上下文不一致
例如列表接口按 `projectId + scriptId` 查出来一条记录，但详情接口只按 `scriptId + episodeId` 查询，而后端校验逻辑更严格，最终导致 404。

---

### 3.4 对后端的明确结论
`剧本拆解` 当前的 404，**大概率不是前端路径写错**，而是：

> **后端分集列表接口与分集详情接口，对同一条 episode 数据的可见性不一致。**

因此后端需要优先核对：

1. `GET /api/projects/{projectId}/scripts/{scriptId}/episodes` 返回的每个 `episodeId`
2. `GET /api/scripts/{scriptId}/episodes/{episodeId}` 是否都能查到
3. 是否存在逻辑删除、状态过滤、租户过滤、权限过滤、项目/剧本关联过滤不一致

---

## 四、问题二：人物小传已有内容，但仍报服务器内部错误

### 4.1 现象复盘
用户明确说明：
- 页面上已经能看到人物小传内容
- 但仍然提示“服务器内部错误”

这意味着：
- **人物小传主查询接口成功了**
- 报错来自同页其他请求，而不是人物小传主数据本身

---

### 4.2 人物小传页面的独立请求组成
文件：`src/views/script/profiles/index.vue`

这个页面不是只请求一个接口，而是同时依赖多个接口：

1. 项目列表
2. 当前项目下剧本列表
3. 人物小传结果
4. 项目分集列表
5. AI 处理状态轮询

因此，只要其中任意一个失败，就可能出现：

- 主内容仍然存在
- 但全局错误提示继续弹出

---

### 4.3 最可疑请求一：AI 处理状态轮询

#### Query Hook
文件：`src/api/queries/ai-process.ts`

```ts
export function useAiProcessStatus(
  params?: MaybeRefOrGetter<Api.AiProcess.StatusSearchParams | undefined>
) {
  return useQuery({
    queryKey: [QUERY_KEY, 'status', params] as const,
    queryFn: async () => {
      const res = await fetchGetAiProcessStatus(toValue(params))
      return res ?? null
    },
    staleTime: 10 * 1000,
    refetchInterval: 5000
  })
}
```

可以看到：
- 它是一个持续轮询接口
- 每 5 秒请求一次
- 如果失败，会反复制造错误提示

#### 页面传参
文件：`src/views/script/profiles/index.vue`

```ts
const aiStatusQuery = useAiProcessStatus(
  computed<Api.AiProcess.StatusSearchParams | undefined>(() =>
    generateRecordId.value && currentScriptId.value
      ? {
          scriptId: currentScriptId.value,
          processType: 'CHARACTER_PROFILE'
        }
      : undefined
  )
)
```

#### API 文档要求
文件：`docs/API/AI-处理记录/api.json`

文档定义的查询参数是：
- `type`
- `businessId`

而不是：
- `scriptId`
- `processType`

所以这里至少存在一个高风险点：

> 前端查询参数结构与 API 文档定义并不一致。

如果中间适配层没有做字段转换，这个轮询接口就可能一直查错。

---

### 4.4 最可疑请求二：项目分集列表
人物小传页面还会请求：

```text
GET /api/projects/{projectId}/episodes
```

这个接口主要用于 AI 生成前给用户展示“可选分集”提示，不是人物小传主内容渲染的必要条件。

因此完全可能发生：
- 人物小传主结果已经查到并显示
- 但项目分集列表接口异常
- 最终仍然弹出“服务器内部错误”

这也解释了为什么用户视觉上已经看到内容，但系统仍在报错。

---

### 4.5 状态值大小写问题会放大异常体验
文件：`src/types/api/api.d.ts`

`Api.AiProcess.ProcessStatus.status` 类型定义为：

```ts
status: 'pending' | 'running' | 'completed' | 'failed'
```

但页面监听判断使用的是：

```ts
if (stage === 'COMPLETED') {
  ...
} else if (stage === 'FAILED') {
  ...
}
```

这意味着：
- 即便状态接口成功返回
- 页面也可能识别不到完成/失败态
- `generateRecordId` 不能及时清空
- 轮询持续执行
- 一旦轮询接口偶发失败，就会重复弹错

所以这个问题虽然不是“服务器内部错误”的唯一来源，但它会显著加重现象。

---

## 五、统一 HTTP 错误处理是问题放大器
本项目当前错误体验差的一个关键原因，是 **全局 HTTP 错误处理没有区分主请求与背景请求**。

也就是说：
- 主页面依赖请求失败，应该提示用户
- 但后台轮询、提示性查询、次级详情查询失败，不一定都应该立即全局弹错

当前两个问题都符合这个特征：

### 剧本拆解
- 列表接口成功
- 次级详情接口失败
- 结果仍全局弹错

### 人物小传
- 主人物小传接口成功
- 轮询或辅助接口失败
- 结果仍全局弹错

因此从产品体验角度看，还存在一个前端架构问题：

> **HTTP 错误展示策略过于激进，未按请求重要性分层。**

---

## 六、最终归因

### 6.1 剧本拆解 404 的最终归因
当前最准确表述是：

> **剧本拆解页显示的分集内容来自分集列表接口，但分集详情接口 `GET /api/scripts/{scriptId}/episodes/{episodeId}` 对同一条记录返回了 404。**

责任大概率在后端，包括：
- 列表与详情数据源不一致
- 列表返回了失效的 `episodeId`
- 详情接口过滤逻辑过严
- 逻辑删除/权限/租户/关联条件不一致

---

### 6.2 人物小传“服务器内部错误”的最终归因
当前最准确表述是：

> **人物小传主内容接口大概率已成功，但页面上的并行请求（尤其是 AI 状态轮询或项目分集列表）仍在失败，而全局错误处理把这些后台失败也直接展示成了“服务器内部错误”。**

其中最可疑的是：

1. `GET /api/ai-process/status`
2. `GET /api/projects/{projectId}/episodes`

同时还叠加了两个前端问题：
- AI 状态查询参数与文档不一致
- 完成态判断使用大写值，和类型定义不一致

---

## 七、前后端排查清单

### 7.1 后端优先排查

#### 针对剧本拆解
1. 核对 `GET /api/projects/{projectId}/scripts/{scriptId}/episodes` 返回的每个 `episodeId`
2. 用这些 `episodeId` 逐个验证 `GET /api/scripts/{scriptId}/episodes/{episodeId}`
3. 检查详情接口是否额外做了：
   - 逻辑删除过滤
   - 状态过滤
   - 项目归属过滤
   - 权限过滤
   - 租户隔离过滤
4. 核查列表查询与详情查询是否来自不同表或不同 VO 装配逻辑

#### 针对人物小传
1. 核查 `GET /api/ai-process/status` 实际后端要求的查询参数名
2. 核查 `businessId` 应该对应 `scriptId` 还是其他业务主键
3. 检查 `GET /api/projects/{projectId}/episodes` 是否存在 500/404/空结果处理不当
4. 确认在人物小传已生成情况下，状态轮询接口是否仍可能返回异常

---

### 7.2 前端优先排查

#### 针对剧本拆解
1. 记录列表接口返回的首条 `episodeId`
2. 对照详情接口实际请求的 `episodeId`
3. 检查页面是否因为自动选中第一条而立即触发详情请求
4. 判断是否可以在详情失败时先降级使用列表数据，不立即全局弹错

#### 针对人物小传
1. 核实 `useAiProcessStatus` 最终发出的 query 参数
2. 核实状态接口是否在页面已有内容时仍持续轮询
3. 核实 `GET /api/projects/{projectId}/episodes` 是否是当前错误来源之一
4. 修正完成态判断与类型定义不一致问题

---

## 八、建议修复优先级

### 第一优先级：先定位真实报错接口
按优先级验证以下三个接口：

1. `GET /api/scripts/{scriptId}/episodes/{episodeId}`
2. `GET /api/ai-process/status`
3. `GET /api/projects/{projectId}/episodes`

这是因为它们最符合“主内容已经显示，但页面依然报错”的特征。

---

### 第二优先级：后端修数据一致性/接口语义
- 修复剧本拆解中列表与详情接口不一致的问题
- 修复 AI 状态接口和项目分集接口对空数据/无记录/异常条件的返回语义

---

### 第三优先级：前端收敛错误展示策略
- 背景轮询失败不要直接全局弹错
- 次级详情查询失败优先在局部提示
- 对非关键请求增加降级兜底

---

### 第四优先级：前端统一数据层与状态逻辑整理
- 剧本拆解补齐统一 Query Hook
- 人物小传轮询参数与文档对齐
- 状态值判断与类型定义统一

---

## 九、最终结论
本次两个问题可以归纳为一句话：

> **不是页面没数据，而是页面在“有主数据”的同时，还存在失败的次级请求；这些失败被统一的全局错误处理直接暴露给用户，造成“明明有内容却还在报错”的现象。**

进一步细分：

- `剧本拆解`：更像是 **后端详情接口与列表接口不一致**
- `人物小传`：更像是 **后台轮询/辅助请求失败 + 前端错误提示过度暴露**

如果后续进入实施阶段，建议按照下面顺序推进：

1. 先确认三个高风险接口的真实返回
2. 再修后端一致性与返回语义
3. 最后修前端的错误分层与轮询收敛
