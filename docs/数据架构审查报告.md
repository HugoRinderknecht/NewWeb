## 二、数据完整流向审计

### 2.1 关键节点

| 节点 | 入口 | 出参 | 备注 |
|------|------|------|------|
| 1. 视图触发 | 按钮 / 路由 | Action / Query Key | 多种入口并存 |
| 2. Store / Query | Action / Composable | API 调用 | Pinia + Vue Query 双轨 |
| 3. API 函数 | 参数 | Promise | 包装适配器 |
| 4. Adapter | RequestConfig | Promise | 抽象层 |
| 5. HTTP 实例 | AxiosRequestConfig | Response | 含拦截器 |
| 6. 后端 | URL + Method | JSON | 跨域代理 |

### 2.2 数据生命周期

```typescript
// 1. 视图层触发
const { data } = useProjectList({ page: 1, size: 10 })
//   ↓
// 2. Vue Query 缓存查询
useQuery({ queryKey: ['projects', params], queryFn: () => fetchGetProjectList(params) })
//   ↓
// 3. API 函数（src/api/project.ts）
export function fetchGetProjectList(params) {
  return getApiAdapter().get<...>('/api/projects', params)
}
//   ↓
// 4. Adapter（src/api/adapter/http-adapter.ts）
return this.request<T>({ ...config, url, method: 'GET', params })
//   ↓
// 5. HTTP 工具（src/utils/http/index.ts）
return request<T>({ url, method, data, params, headers, signal, responseType })
//   ↓
// 6. axios 拦截器
//   - 请求：自动注入 Authorization: Bearer {token}
//   - 响应：code 校验，401 自动 logout
//   ↓
// 7. 后端服务（http://server.bsuniversal.cn:10006）
```

### 2.3 存储环节

| 数据 | 存储位置 | 持久化策略 | 风险 |
|------|---------|-----------|------|
| accessToken | `useUserStore` | sessionStorage | 关闭浏览器即失效，合理 |
| refreshToken | `useUserStore` | sessionStorage | 同上 |
| currentProjectId | `useProjectStore` | sessionStorage | 跨标签页同步性需关注 |
| pendingCount | `useReviewStore` | sessionStorage | 同上 |
| unreadCount | `useNotificationStore` | sessionStorage | 同上 |
| 路由菜单 | `useMenuStore` | 不持久化 | 重新登录需重新拉取 |
| Vue Query 缓存 | 内存 | 刷新即清 | 需配合 store 持久化 |

## 三、模块内部数据交互机制

### 3.1 统一做法

- **Pinia Store**：`defineStore('module', () => { state, getters, actions })` 组合式风格
- **Vue Query**：`useQuery` / `useMutation` 包装，自动缓存 + 失效
- **HTTP 工具**：所有 API 走 `getApiAdapter().xxx()`，由 `HttpAdapter` 委托给 `request` 对象

### 3.2 不一致做法

| 现象 | 出现位置 | 影响 |
|------|---------|------|
| Pinia + 手动 API 调用 | `src/api/script.ts` 等 | 失去 Vue Query 缓存与失效管理 |
| Vue Query | `src/api/queries/*.ts` | 缓存可控，但与 Pinia 状态易重复 |
| 双 Store 模式 | `useProjectStore` + `useProjectDataStore` | 同步逻辑分散在两处 |
| 客户端过滤 vs 服务端搜索 | 菜单管理 | 大数据量时性能差 |
| 硬编码 Mock 数据 | `team/quota`、`gpt-image/tasks` 等 | 真实数据接入前需替换 |

### 3.3 数据一致性保障

| 保障手段 | 实现 | 评价 |
|---------|------|------|
| 401 自动登出 | `utils/http/index.ts:120` | ✅ 全局有效 |
| 请求去重 | `pendingRequests` Map | ✅ 仅对 GET 生效 |
| 响应缓存（TTL） | `responseCache` + `cacheTTL` | ⚠️ 默认未启用 |
| 乐观更新 | `useReviewStore.decrementPending` | ✅ 局部 |
| 跨 Store 同步 | `currentProjectId` 双向同步 | ⚠️ 容易遗漏 |
| WebSocket 推送 | `notification-ws.ts` | ✅ 通知模块有效 |

### 4.3 关键问题

#### 问题 1：API 模块重复（严重）

**位置**：
- `src/api/admin/user-manage.ts` vs `src/api/system-manage.ts`
- `src/api/admin/team-manage.ts` vs `src/api/team.ts`
- `src/api/admin/billing-config.ts` vs `src/api/billing.ts`
- `src/api/admin/audit-log.ts` vs 审计日志实现
- `src/api/admin/dashboard.ts` vs `src/api/statistics.ts`

**影响**：
- 同一功能两套实现，行为可能不一致
- 维护成本翻倍
- 文档中已明确指出但未修复

**建议**：废弃 `src/api/admin/*`，统一迁移到 `src/api/*.ts` 顶层。

#### 问题 2：菜单接口版本不一致（中等）

**位置**：`src/api/system-manage.ts` 中 `GET /api/v3/system/menus/simple`  
**其他接口**：`/api/v1/...` 或 `/api/v2/...` 或无前缀

**建议**：统一版本策略，或移除 `/api/v3/` 前缀。

#### 问题 3：双 Store 数据同步风险（中等）

**位置**：`useProjectStore` ↔ `useProjectDataStore`

**当前同步方式**：通过 `currentProjectId` 双向同步  
**风险**：一方更新失败时，另一方仍持有旧值

**建议**：评估合并为单一 Store。

#### 问题 4：缺失 MockAdapter（架构层）

**期望**：`MockAdapter` 与 `HttpAdapter` 同级，提供离线/测试环境  
**实际**：仅 `HttpAdapter` 一个实现（参考 README 中提到 MockAdapter 但代码中无）

**建议**：在 `src/api/adapter/` 中补充 `MockAdapter`，用于：
- 离线开发
- 单元测试
- 演示环境

## 五、Adapter 层规范性审计

### 5.1 适配器接口定义（合规）

```typescript
// src/api/adapter/types.ts
export interface IApiAdapter {
  request<T>(config: RequestConfig): Promise<T>
  get/post/put/del/patch<T>(...): Promise<T>
}
```

✅ 接口清晰，方法完整。  
✅ `HttpAdapter` 实现严格遵守接口契约。  
✅ 提供 `getApiAdapter()` 单例 + `resetAdapter()` 用于测试注入。

### 5.2 实际使用情况

- **45 个文件**通过 `getApiAdapter()` 获取适配器
- **0 个文件**直接 `import axios`（已抽离到 `utils/http`）
- **0 个文件**绕过适配器直接 fetch（经抽查）

✅ Adapter 抽象被广泛采用，符合分层原则。

### 5.3 仍可改进

| 改进点 | 当前 | 建议 |
|--------|------|------|
| 错误转换 | `HttpAdapter` 透传 `HttpError` | 在 Adapter 层加 retry/transform |
| 流式响应 | `responseType: 'stream'` 已支持但无 wrapper | 抽象 `createStreamAdapter` |
| 类型安全 | `data?: any` `params?: any` | 改为泛型 + 类型推断 |
| 拦截器位置 | 拦截器在 `utils/http`，不在 Adapter | 将拦截器下沉到 Adapter 内部更内聚 |
| 切换 Mock | `resetAdapter()` 但无 Mock 实现 | 实现 `MockAdapter` |

### 5.4 数据隔离

| 隔离维度 | 实现 | 评价 |
|---------|------|------|
| 项目隔离 | API 携带 `projectId` | ✅ URL 隔离 |
| 团队隔离 | API 携带 `teamId` | ✅ URL 隔离 |
| 用户隔离 | Token + 后端校验 | ✅ |
| 客户端隔离 | `withCredentials: false` | ⚠️ 跨域时无法共享 Cookie |
| 缓存隔离 | `pendingRequests` key = method+url+params | ⚠️ 不同用户复用 key 风险 |

## 六、关键节点 / 数据孤岛 / 冗余

### 6.1 数据孤岛

| 孤岛 | 表现 | 风险 |
|------|------|------|
| `useScriptProjectStore` | 与 `useProjectStore` 关系不明确 | 切换项目时可能不同步 |
| 通知 WebSocket | 独立 WS 连接 | 与 Vue Query 缓存不联动 |
| 路由权限缓存 | 静态路由 + 动态菜单 | 角色变更后需重新登录 |
| `useWorktabStore` | 工作台标签 | 与项目切换不联动 |
| 草稿数据 | 编辑器本地 | 关闭浏览器即丢失 |

### 6.2 数据冗余

| 冗余 | 位置 | 建议 |
|------|------|------|
| 用户信息在多 Store 镜像 | user / menu / team | 统一从 userStore getter 获取 |
| 项目信息 | project / project-data / script-project | 收敛到 projectStore |
| API 重复定义 | admin/* vs 顶层 | 废弃 admin/* |
| 标签数据 | asset / script-asset | 共享独立 endpoint |
| 状态枚举 | 各 view 内重复定义 | 提到 `types/` 统一 |

### 6.3 不符合架构规范的实现

| 编号 | 位置 | 问题 |
|------|------|------|
| AR-1 | `src/api/admin/*.ts` 7 个文件 | 与顶层 `src/api/*.ts` 平行重复 |
| AR-2 | `src/api/episode.ts` | 函数命名风格不统一（无 `fetch` 前缀） |
| AR-3 | `src/api/dify.ts` | 与 `src/api/workflow.ts` 功能重叠 |
| AR-4 | 部分 view | 直接调用 `useUserStore().xxx` 而非 getter |
| AR-5 | `src/api/system-manage.ts` | 菜单接口 `/api/v3/` 命名不一致 |
| AR-6 | `src/types/api/api.d.ts` | `Api.AiProcess` 命名空间定义重复 |
| AR-7 | `src/api/script.ts` | 未走 Vue Query，与 project 模块不一致 |

## 七、评估结论

### 7.1 总体评价

项目**整体架构合理**，采用了 Adapter + Pinia + Vue Query 的现代前端分层方案：
- ✅ Adapter 抽象到位
- ✅ HTTP 拦截器统一
- ✅ 大部分模块走规范流程
- ⚠️ Admin 平行 API 模块属于历史遗留
- ⚠️ Vue Query 仅部分模块使用
- ⚠️ Mock 缺失影响开发与测试

### 7.2 风险等级

| 维度 | 评分 | 说明 |
|------|------|------|
| 数据流向清晰度 | ⭐⭐⭐⭐ | 大部分链路可追踪 |
| 一致性保障 | ⭐⭐⭐ | 局部完善，全局欠缺 |
| Adapter 规范性 | ⭐⭐⭐⭐ | 抽象有效，缺 Mock |
| 跨模块通信 | ⭐⭐⭐ | 依赖 URL 携带 ID，缺少统一事件总线 |
| 数据隔离 | ⭐⭐⭐ | URL + Token，后端校验为主 |
| 整体可维护性 | ⭐⭐⭐ | 重复模块需清理 |

### 7.3 优先改进建议

1. **P0 立即处理**：合并 `src/api/admin/*` 到顶层 API
2. **P0 立即处理**：补充 `MockAdapter` 实现
3. **P1 短期**：统一菜单接口版本号
4. **P1 短期**：扩展 Vue Query 覆盖范围
5. **P2 中期**：合并 `useProjectStore` 与 `useProjectDataStore`
6. **P2 中期**：抽象 `types/` 下的重复枚举
7. **P3 长期**：引入事件总线（mitt 已有依赖）用于跨模块通信
