## 1. 执行摘要

### 1.1 审查结论

本项目当前存在 **三套并行的数据获取范式**、**7 组重复 API 调用**、**三套缓存机制互不相通** 的问题。引入统一数据层 **可行且收益显著**，预计可减少 30-40% 的重复代码、消除跨页面数据不一致、降低新功能开发成本。

### 1.2 核心发现

| 维度 | 现状 | 问题严重度 |
|------|------|-----------|
| 数据获取范式 | 3 种并存 (直接调用 / useTable / vue-query) | 🔴 高 |
| 重复 API 调用 | 7 组端点被 2-4 处独立调用 | 🔴 高 |
| 缓存策略 | 3 套独立缓存，互不共享 | 🟡 中 |
| 状态管理 | 11 个 Store，3 个 Project Store 职责重叠 | 🔴 高 |
| 数据转换 | 大部分内联处理，仅 1 个 transformer 文件 | 🟡 中 |
| 错误处理 | 3 种不同的错误/加载状态管理模式 | 🟡 中 |
| 加载状态 | 各页面自行管理，无统一模式 | 🟢 低 |

### 2.2 三套数据获取范式详解

#### 范式 A: 直接 API 调用 (约 60% 页面)

**特征**: 组件 `onMounted` 中直接调用 `fetchXxx()` 函数，使用本地 `ref()` 管理 `loading`/`data`/`error`。

**典型代码模式**:
```typescript
// src/views/team/list/index.vue
const loading = ref(false)
const teamList = ref<TeamItem[]>([])

const loadTeams = async () => {
  loading.value = true
  try {
    const res = await fetchGetMyTeams()
    teamList.value = (res as any)?.records || res || []
  } catch { /* 静默失败 */ }
  finally { loading.value = false }
}

onMounted(() => { loadTeams() })
```

**使用此范式的页面** (部分列表):

| 页面 | API 端点 | 本地状态管理 |
|------|---------|-------------|
| `views/team/list/index.vue` | `fetchGetMyTeams` | `ref<TeamItem[]>` + 手动 loading |
| `views/review/content/index.vue` | `fetchGetReviewList` | `ref<ReviewItem[]>` + 手动 loading |
| `views/workflow/list/index.vue` | `fetchGetWorkflowList` | `ref<any[]>` + 手动 loading |
| `views/points/billing/index.vue` | `fetchGetMyCredits` | `ref` + 内联转换 |
| `views/notice/site/index.vue` | `fetchGetNotificationList` | `ref` + mock fallback |
| `views/data-history/records/index.vue` | `fetchGetDataHistoryList` | `reactive({page, limit, total})` |
| `views/asset/library/index.vue` | `fetchGetProjectAssets` | `ref` + store 仅取 projectId |
| `views/video-gen/history/index.vue` | `fetchGetVideoTaskList` | 服务端分页 |
| `views/settings/account/index.vue` | `fetchGetUserInfo` | `ref` 本地存储 |
| `views/dashboard/console/modules/recent-project.vue` | `fetchGetProjectList` | `ref` + 动画转换 |
| `views/dashboard/console/modules/pending-review.vue` | `fetchGetPendingReviewCount` + `fetchGetReviewList` | `Promise.all` 并行 |
| `views/dashboard/console/modules/latest-notice.vue` | `fetchGetNotificationList` | `ref` + 内联映射 |

#### 范式 B: useTable Hook (约 20% 页面)

**特征**: 使用 `src/hooks/core/useTable.ts` 自定义 Hook，自动处理 API 调用、分页、缓存、搜索防抖、请求取消。

**典型代码模式**:
```typescript
// src/views/system/user/index.vue
const { data, loading, pagination, getData, refreshData } = useTable({
  core: {
    apiFn: fetchGetUserList,
    columnsFactory: createUserColumns,
    excludeParams: ['daterange']
  }
})
```

**使用此范式的页面**: 系统管理模块 (user, role 等 CRUD 表格页面)

**useTable 提供的能力**:
- `TableCache` 类: 可配置 TTL (默认 5 分钟)、最大容量、命中率追踪、4 种失效策略
- `AbortController` 请求取消
- 5 种刷新策略: `refreshCreate`, `refreshUpdate`, `refreshRemove`, `refreshData`, `refreshSoft`
- `LoadingState` 状态机: `idle → loading → success/error`
- `defaultResponseAdapter`: 自动适配多种 API 响应格式

#### 范式 C: TanStack Vue Query (约 10% 页面)

**特征**: 使用 `src/api/queries/` 下的 composable 函数，基于 `@tanstack/vue-query` v5，提供自动缓存、去重、后台刷新、loading/error 状态。

**典型代码模式**:
```typescript
// src/views/stats/dashboard/index.vue
const { data: dashboardData, isLoading: dashboardLoading } = useStatsDashboard()
const { data: realtimeData } = useStatsRealtime()
```

**已封装的 Vue Query 模块**:

| 模块 | 查询数 | 变更数 | 覆盖范围 |
|------|--------|--------|---------|
| `statistics.ts` | 18 | 5 | 统计仪表盘、实时数据、趋势、积分、告警、排名等 |
| `project.ts` | 7 | 9 | 项目 CRUD、成员、配置、审核、统计、剧集 |
| `storyboard.ts` | 7 | 10 | 分镜 CRUD、版本、图片、场景、拆解/重建 |

**Vue Query 全局配置** (`src/plugins/vue-query.ts`):
```typescript
{
  refetchOnWindowFocus: false,
  retry: 1,
  staleTime: 5 * 60 * 1000,   // 5 分钟
  gcTime: 10 * 60 * 1000       // 10 分钟
}
```

### 2.4 缓存层现状

项目当前存在 **三套独立的缓存机制**:

| 缓存层 | 位置 | TTL | 失效策略 | 共享性 |
|--------|------|-----|---------|--------|
| Axios 响应缓存 | `utils/http/index.ts` | 按请求配置 | 手动 | ❌ 仅限 HTTP 层 |
| useTable TableCache | `utils/table/tableCache.ts` | 5 分钟 (可配置) | CLEAR_ALL / CLEAR_CURRENT / CLEAR_PAGINATION / KEEP_ALL | ❌ 仅限 useTable |
| Vue Query 缓存 | `@tanstack/vue-query` | staleTime: 5min, gcTime: 10min | queryKey 匹配 + 手动 invalidate | ❌ 仅限 vue-query composables |

**问题**: 三套缓存互不通信。一个通过 vue-query 获取的项目列表和一个通过直接 API 调用获取的项目列表，即使使用同一个端点，也不会共享缓存。

### 2.5 实时数据通道

| 通道 | 技术 | 用途 | 数据去向 |
|------|------|------|---------|
| SSE | `utils/http/sse.ts` (原生 fetch) | AI 工作流流式响应 | 组件直接消费 |
| WebSocket | `utils/socket/index.ts` | 通知推送 | `notificationStore.incrementUnread()` |
| DataFlow Bus | `utils/data-flow/bus.ts` | 内部 pub/sub | 桥接 Store 到组件 |

## 3. 问题诊断与分析

### 3.1 重复 API 调用 (7 组)

以下 API 端点被多个位置独立调用，**无共享缓存**:

#### 3.1.1 `fetchGetReviewList` — 3 处独立调用

```
├── views/review/content/index.vue          ← 页面级直接调用
├── views/dashboard/console/modules/pending-review.vue  ← Widget 直接调用
└── store/modules/review.ts                 ← Store loadReviewList action (未被使用)
```

**影响**: 用户在审核中心浏览审核列表后，回到仪表盘看到的可能是不同步的数据。

#### 3.1.2 `fetchGetPendingReviewCount` — 2 处独立调用

```
├── views/dashboard/console/modules/pending-review.vue  ← Widget 直接调用
└── store/modules/review.ts                 ← Store loadPendingCount action
```

#### 3.1.3 `fetchGetNotificationList` — 3 处独立调用

```
├── views/notice/site/index.vue             ← 页面级直接调用
├── views/dashboard/console/modules/latest-notice.vue  ← Widget 直接调用
└── store/modules/notification.ts           ← Store loadNotifications action
```

#### 3.1.4 `fetchGetProjectList` — 4 处独立调用 (最严重)

```
├── views/dashboard/console/modules/recent-project.vue  ← Widget 直接调用
├── store/modules/project.ts                ← Store loadProjectList
├── store/modules/project-data.ts           ← Store loadProjects
└── api/queries/project.ts                  ← Vue Query useProjectList
```

**影响**: 同一个 API 端点被 4 个不同位置独立调用，各自维护独立的缓存和状态。

#### 3.1.5 `fetchGetMyTeams` — 3 处独立调用

```
├── views/team/list/index.vue               ← 页面级直接调用
├── views/dashboard/console/index.vue       ← 入驻检查直接调用
└── store/modules/team.ts                   ← Store loadTeamList action
```

#### 3.1.6 `fetchGetMyCredits` — 2 处独立调用

```
├── views/points/billing/index.vue          ← 页面级直接调用
└── api/queries/statistics.ts               ← Vue Query useMyCredits
```

#### 3.1.7 Project Store 三重奏 — `fetchGetProjectList` 被 3 个 Store 独立调用

```
store/modules/project.ts      → fetchGetProjectList (loadProjectList)
store/modules/project-data.ts → fetchGetProjectList (loadProjects)
api/queries/project.ts        → fetchGetProjectList (useProjectList)
```

三个模块各自维护 `currentProjectId` 并通过 `setCurrentProject` 交叉调用同步，但各自拥有独立的数据数组。这是一个 **脆弱的同步链**。

### 3.2 数据转换碎片化

#### 3.2.1 内联转换 vs Transformer 文件

项目有 `utils/transformers/team.transformer.ts` 提供了标准化的 `transformTeamMember()` 函数，但 **99% 的页面仍在使用内联 `.map()` 转换**:

| 页面 | 内联转换内容 | 是否可提取 |
|------|-------------|-----------|
| `team/list/index.vue` | `teamId→id`, `teamName→name`, `status→active/archived` | ✅ |
| `workflow/list/index.vue` | `code→workflowCode`, `enabled→enabled/disabled` | ✅ |
| `dashboard/modules/recent-project.vue` | `projectName→name`, `progress→percentage` | ✅ |
| `notice/site/index.vue` | `status→已读/未读` | ✅ |
| `points/billing/index.vue` | 积分账单格式化 | ✅ |
| `review/content/index.vue` | 审核状态映射 | ✅ |

#### 3.2.2 状态标签映射重复定义

以下常量在多个页面中各自定义:

```
审核状态 (pending/approved/rejected):
  ├── views/review/content/index.vue          ← 本地定义
  ├── views/dashboard/modules/pending-review.vue  ← 本地定义
  └── store/modules/review.ts                 ← 本地定义

资产类型标签/颜色:
  ├── views/asset/library/index.vue           ← 本地定义
  └── views/script/version/index.vue          ← 本地定义 (略有不同)

角色标签 (owner/admin/member):
  └── views/team/list/index.vue               ← 本地定义
```

### 3.3 错误处理不一致

| 错误处理模式 | 使用范围 | 问题 |
|-------------|---------|------|
| 裸 `catch {}` 静默吞错 | 大部分页面 | 错误丢失，无法追踪 |
| `ElMessage.error()` 通用提示 | 部分页面 | 无结构化错误信息 |
| `createErrorHandler` 结构化错误 | useTable 仅 | 覆盖面窄 |
| `HttpError` + `errorMap` 业务错误码 | `auth/forget-password` 仅 | 未推广 |
| Mock 数据 fallback | `notice/site` | 掩盖了真实错误 |

### 3.4 加载状态管理不一致

| 模式 | 实现 | 使用范围 |
|------|------|---------|
| 手动 `loading` ref + try/finally | `const loading = ref(false)` | ~60% 页面 |
| useTable 状态机 | `LoadingState: idle/loading/success/error` | ~20% 页面 |
| Vue Query `isLoading`/`isError` | 自动管理 | ~10% 页面 |
| 无加载状态 | 部分 Widget | 少量组件 |

## 5. 统一数据层设计方案

### 5.1 架构设计: 双轨互补模式

推荐采用 **TanStack Vue Query (服务端状态) + Pinia (客户端状态)** 的互补架构:

```
┌─────────────────────────────────────────────────────────────┐
│                       Vue 组件层                              │
│                                                               │
│    const { data, isLoading } = useXxx()  ← 声明式获取         │
│    const mutation = useXxxMutation()      ← 声明式变更         │
│    const { user, team } = useAppStore()   ← 客户端状态        │
│                                                               │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  ┌─────────────────────────┐  ┌─────────────────────────┐   │
│  │   Vue Query 层           │  │   Pinia Store 层         │   │
│  │   (服务端状态)            │  │   (客户端状态)            │   │
```

### 5.2 职责划分原则

| 数据类型 | 管理者 | 理由 |
|---------|--------|------|
| 服务端状态 (API 数据) | **Vue Query** | 自动缓存、去重、后台刷新、失效策略 |
| 客户端状态 (UI/会话) | **Pinia** | 持久化、同步访问、跨组件共享 |
| 表格数据 (分页/搜索) | **useTable (改造)** | 已有成熟模式，内部使用 Vue Query |
| 实时数据 (SSE/WS) | **专用 composable** | 特殊生命周期，不适合标准缓存 |

**判断标准**: 如果数据来自 API 且可以重新获取 → Vue Query。如果数据是纯客户端的 (主题、标签页、当前选择) → Pinia。

### 6.3 StaleTime 策略

| 数据类型 | staleTime | 理由 |
|---------|-----------|------|
| 高频变化 (审核数量、通知) | 10s - 30s | 需要及时反映最新状态 |
| 中频变化 (列表数据、统计数据) | 30s - 60s | 平衡新鲜度和性能 |
| 低频变化 (项目配置、团队信息) | 5min | 变更不频繁 |
| 静态数据 (枚举、字典) | 30min | 几乎不变 |
| 实时数据 (轮询) | 0 + refetchInterval | 始终获取最新 |

## 7. 与现有系统的兼容性处理

### 7.1 迁移策略: 渐进式替换

**核心原则**: 不做大规模重写，采用 **并行运行 → 逐模块切换 → 清理旧代码** 的三步走策略。

```
Phase 1: 新增 Vue Query composables (与现有代码并行)
    ↓
Phase 2: 新页面/重构页面使用新 composables
    ↓
Phase 3: 逐页面迁移现有页面
    ↓
Phase 4: 清理废弃的 Store actions 和直接调用
```

### 7.2 Store 与 Vue Query 共存方案

| 场景 | 处理方式 |
|------|---------|
| Store 中的持久化状态 (currentProjectId) | **保留** 在 Pinia，Vue Query 通过 `enabled` 参数依赖它 |
| Store 中的 API 数据 (projectList) | **迁移** 到 Vue Query，Store 仅保留 getter 代理 |
| Store 中的 WebSocket 状态 | **保留** 在 Pinia，通过 queryClient.invalidateQueries 桥接 |
| 组件同时需要 Store 状态 + API 数据 | 组合使用: `const { currentProjectId } = useProjectStore()` + `const { data } = useProjectDetail(currentProjectId)` |

### 7.3 useTable 兼容方案

**策略**: 内部改造为 Vue Query，对外保持 API 不变。

```typescript
// 改造前 (组件代码无需修改)
const { data, loading, pagination, getData, refreshData } = useTable({
  core: { apiFn: fetchGetUserList, columnsFactory: createUserColumns }
})

// 改造后 useTable 内部
export function useTable(config) {
  // 内部用 Vue Query 替代手动 API 调用
  const query = useQuery({
    queryKey: [QUERY_KEYS.TABLE, apiFn.name, computedParams],
    queryFn: () => apiFn(searchParams.value),
    ...mapConfigToQueryOptions(config),
  })

  // 保持原有返回接口
  return {
    data: computed(() => transformData(query.data.value)),
    loading: computed(() => query.isLoading.value),
    // ...
  }
}
```

### 7.4 逐步迁移顺序 (按依赖关系)

```
第一优先: 无依赖的独立模块
  ├── notification (通知) → 简单，影响面小，可验证模式
  ├── review (审核) → 有重复调用问题，收益明显
  └── points (积分) → 简单模块

第二优先: 有跨页面共享需求的模块
  ├── team (团队) → 多处使用，消除重复
  ├── asset (资产) → 多页面使用
  └── project (项目) → 最复杂，需要合并 3 个 Store

第三优先: 复杂交互模块
  ├── script (剧本) → 依赖 project
  ├── storyboard (分镜) → 部分已有 vue-query
  └── video-gen (视频生成) → 有 SSE 特殊需求

第四优先: 管理后台模块
  └── system/* (系统管理) → useTable 已覆盖，改动最小
```

### 7.5 保持向后兼容

| 现有模式 | 兼容方案 |
|---------|---------|
| 组件中 `fetchXxx()` 直接调用 | 继续可用，新页面使用 composable |
| Store actions `loadXxx()` | 保留为 deprecated，内部委托给 Vue Query |
| `useTable` hook | 内部改造，外部 API 不变 |
| SSE/WebSocket | 不受影响，通过 invalidateQueries 桥接 |
| DataFlow Bus | 可选桥接，或逐步弃用 |

## 10. 风险评估与缓解策略

### 10.1 技术风险

| 风险 | 可能性 | 影响 | 缓解策略 |
|------|--------|------|---------|
| Vue Query 与 Pinia 持久化状态冲突 | 低 | 中 | 严格划分: Vue Query 管服务端状态，Pinia 管客户端状态。通过 `enabled` 参数让 Query 依赖 Store 状态 |
| useTable 改造引入 regression | 中 | 高 | 保持外部 API 不变，内部改造。先在非关键页面验证 |
| SSE/WebSocket 数据与 Vue Query 缓存不一致 | 中 | 中 | WebSocket 消息到达时调用 `queryClient.invalidateQueries()`。SSE 流式数据不走缓存 |
| 3 个 Project Store 合并导致遗漏 | 中 | 高 | 先写完整的集成测试，再执行合并。逐步替换而非一次性删除 |

### 10.2 项目风险

| 风险 | 可能性 | 影响 | 缓解策略 |
|------|--------|------|---------|
| 迁移期间新功能开发冲突 | 高 | 中 | 制定明确的分支策略: 迁移工作在 feature 分支进行，定期从 main 合并 |
| 12 周工期被业务需求打断 | 高 | 中 | 每个 Phase 独立可交付，中断后可从下一 Phase 继续 |
| 团队成员对 Vue Query 不熟悉 | 低 | 低 | 项目已有 Vue Query 使用经验 (statistics/project/storyboard)，可作为学习模板 |

### 10.3 回滚方案

每个 Phase 都有独立的回滚方案:

- **Phase 1**: 删除新增文件即可，无现有代码改动
- **Phase 2**: 恢复迁移前的页面代码，恢复 Store actions
- **Phase 3**: 恢复 Store 文件，恢复页面代码
- **Phase 4**: 同 Phase 2/3

**关键保障**: 每个 Phase 的改动都在独立的 Git 分支进行，通过 PR review 后合并。
