# 核对结论

## 范围

- 基于 `docs/API接口对比报告.md` 中列出的 5 类问题进行交叉核对。
- 覆盖 `src/api`、`src/api/adapter`、`src/store/modules`、`src/views`、`src/types/api/api.d.ts`、`src/main.ts`。

## 逐项核对记录

### 1) 剧本 `projectId/scriptId` 混淆

- `src/store/modules/script-project.ts` 当前只保存 `currentProjectId`，没有 `currentScriptId`。
- 报告中列出的剧本视图调用模式，与当前 store 字段设计不匹配。
- 目前可确认：报告对“存在参数混淆风险”的判断成立。

### 2) 资产 `projectId` 硬编码 `'1'`

- `src/store/modules/project-data.ts` 中 `currentProjectId` 初始值为 `'1'`，且 `projects` 数组是静态 mock 数据。
- `src/main.ts` 的 `bootstrap()` 只做了 `initStore`、`setupVueQuery`、`initRouter` 等初始化，没有看到项目数据加载动作。
- 因此报告中关于硬编码和 mock 占位值会导致请求错误的结论成立。

### 3) 团队 `teamId` 缺失

- 当前可直接确认：store 层没有提供报告中建议的统一团队兜底来源。
- 报告描述的页面取值方式与这个 store 现状相匹配，因此该问题成立。
- 但“所有列出的视图都一定失败”这一点建议在后续修复时再做页面级实际验证。

### 4) 趋势接口缺少 `eventType`

- `src/api/statistics.ts` 的 `fetchGetTrends` 允许 `params` 省略，函数体未强制注入 `eventType`。
- `src/views/dashboard/console/modules/sales-overview.vue` 当前确实直接调用 `fetchGetTrends()`。
- 该问题可直接确认存在。

### 5) adapter 被绕过

- `src/api/adapter/index.ts` 已实现 `getApiAdapter()`、`HttpAdapter`、`MockAdapter`、`HybridAdapter`。
- 但现有 API 文件示例 `src/api/auth.ts` 仍直接使用 `@/utils/http`。
- 说明“适配器存在但未统一使用”的判断成立。

## 需要进一步确认的部分

- 报告中“53 个文件”“22/24 模块”“约 60% / 20% / 60 个函数”等统计值，当前已能确认方向正确，但精确数字仍需要逐模块枚举验证。
- 报告中提到的“缺失函数清单”和“新增函数清单”，建议后续继续做模块级对表，避免漏项或重复计数。

## 总体判断

- 报告中提出的 5 类核心问题，当前代码证据支持其结论，属于“已确认问题”。
- 其中最需要优先处理的是：
  1. `projectId/scriptId` 混用
  2. `projectId='1'` 与静态 mock 项目数据
  3. `teamId` 兜底缺失
  4. `fetchGetTrends()` 无 `eventType`
  5. API 层仍未统一接入 adapter
