# Dreamcraft Astra 前端数据层架构审查报告

> **报告日期**：2026 年 6 月 7 日\
> **项目名称**：Dreamcraft Astra\
> **报告类型**：前端数据层架构专项审查报告\
> **审查重点**：数据处理逻辑与 UI 组件分离程度、数据获取、状态管理、数据转换、缓存策略、错误处理机制、后续分层优化方案

***

# 一、审查目标与范围

本次审查聚焦当前前端项目的数据层架构设计，重点评估数据处理逻辑与 UI 组件之间的分离程度，并分析以下关键方面：

- 数据请求与业务逻辑的耦合度
- 状态管理方案的职责划分与合理性
- 数据模型与接口抽象程度
- 数据转换逻辑的归属是否清晰
- 多层缓存机制的有效性与一致性
- 错误处理机制的完备性与可维护性
- 数据层进一步解耦与模块化演进的可实施路径

本次分析基于项目当前代码结构、核心数据流实现方式以及典型页面模块的实现现状展开。

***

# 二、总体结论

从整体架构上看，当前项目已经具备较为成熟的数据层基础设施，形成了较清晰的技术分层雏形，尤其在以下方面表现较好：

- 已建立统一 HTTP 请求封装与鉴权处理机制
- 已引入 TanStack Vue Query 管理服务端状态
- 已使用 Pinia 管理客户端状态与会话状态
- 已开始将部分 Store 收敛为 UI 状态容器
- 已具备 API Adapter、Transformer、Data Flow 等抽象意识
- 已存在请求去重、缓存、重试、401 自动刷新等治理能力

但从“数据层是否真正与 UI 解耦”这一目标来看，当前项目仍然处于**过渡型架构阶段**。

即：

- 一部分模块已经实现了“服务端状态归 Query、UI 状态归 Store、页面只负责展示”的理想模式；
- 另一部分模块仍然存在“页面组件直接拼装数据、处理业务分支、管理批量操作流程、兼容后端字段差异”的情况。

因此，当前项目的核心问题不是“缺少数据层”，而是**数据层边界尚未完全统一，职责划分在不同模块之间存在不一致现象**。

综合判断：

- **数据层基础能力：较强**
- **分层意识：明确**
- **UI 与数据逻辑分离程度：中等偏上，但不稳定**
- **后续优化重点：统一领域抽象与职责边界**

***

# 三、当前数据层总体结构分析

从项目结构看，当前前端数据相关实现大致可以分为五个层次：

## 3.1 基础设施层

主要负责网络请求、错误处理、认证、缓存底层能力。

典型位置：

- `src/utils/http/*`
- `src/utils/storage/*`
- `src/plugins/vue-query.ts`

这一层承担：

- Axios 实例创建
- 请求/响应拦截器
- Token 注入与刷新
- 请求重试
- 请求去重
- 响应缓存
- 错误转换与统一提示
- QueryClient 初始化

## 3.2 API 访问层

主要负责定义远程接口访问函数。

典型位置：

- `src/api/*.ts`
- `src/api/adapter/*`

这一层的优点是：

- 已将接口地址、请求方法、参数形式从页面中抽离
- 通过 Adapter 统一了访问入口
- 页面通常不直接操作 Axios

## 3.3 Query Hook 层

主要负责：

- 服务端状态缓存
- queryKey 管理
- 失效策略
- enabled 控制
- mutation 后缓存刷新

典型位置：

- `src/api/queries/*.ts`

这是当前项目“数据层现代化程度”最高的一层，也是后续继续演进的核心基础。

## 3.4 本地状态层

主要负责：

- UI 状态
- 会话态
- 本地偏好配置
- 页面选择状态
- 业务域切换状态

典型位置：

- `src/store/modules/*.ts`

目前项目已经开始把一部分 Store 从“业务数据仓库”转向“纯 UI 状态容器”，方向正确。

## 3.5 页面与组件层

主要位置：

- `src/views/**`
- `src/components/**`

当前主要问题集中在这一层：

- 页面组件中仍存在一定比例的数据拼装逻辑
- mutation 编排与批量业务流程仍部分留在页面中
- 某些页面承担了 ViewModel 层职责

# 四、数据获取实现方式审查

## 4.1 优点：接口调用已基本脱离视图组件

当前项目多数接口已经采用如下模式：

1. `src/api/*.ts` 中定义原始接口函数
2. `src/api/queries/*.ts` 中封装 query / mutation hook
3. 页面组件直接使用 hook 而不是直接发请求

这意味着：

- 页面层与网络请求底层耦合较低
- 请求参数与接口地址集中管理
- 缓存与失效规则开始向 Query 层集中
- 为测试和后续替换数据源预留了空间

例如项目列表、项目详情、成员列表、统计数据、分镜列表等模块均已体现这一模式。

## 4.2 问题：Query Hook 层偏“薄封装”，领域语义不足

虽然 Query Hook 已经存在，但不少 Hook 的职责仍偏向“把 API 再包一层”，而没有完全承担起领域抽象职责。

表现为：

- queryKey 定义较分散
- 某些 key 与真实依赖关系不完全一致
- 缺少统一的 key 工厂
- Hook 对结果数据的结构整理较少
- 很多 Hook 直接返回后端原始结构或轻度加工结构

这会导致：

- 页面仍需理解后端字段结构
- 页面仍需处理空值、fallback 与兼容情况
- 领域数据模型没有形成统一出口

## 4.3 问题：部分页面仍承担多接口组合与派生计算职责

在一些看板页、统计页、业务页中，页面组件仍直接负责：

- 同时调用多个 Query Hook
- 自行合并不同接口返回值
- 自行做字段兼容
- 自行计算图表数据与汇总指标
- 自行决定 fallback 数据来源

这类逻辑虽然表面上仍位于“页面内部”，但本质上已经不是单纯展示逻辑，而是：

- 视图模型构造逻辑
- 页面级数据聚合逻辑
- 领域派生逻辑

这部分如果继续停留在组件中，会直接影响：

- 页面可读性
- 复用性
- 单元测试可写性
- 数据格式升级时的改造成本

### 结论

当前数据获取链路已经具备较好的基础分层，但 Query 层仍需进一步从“接口缓存层”演进为“领域数据组织层”。

# 五、状态管理方案审查

## 5.1 总体评价

当前项目采用：

- **Vue Query** 管理服务端状态
- **Pinia** 管理客户端状态、持久化状态和局部会话状态

这是合理且符合现代前端架构趋势的。

## 5.2 优点：服务端状态与 UI 状态已经开始分离

部分 Store 中已经明确写出：

- 服务端数据统一通过 Query Hook 获取
- Store 只保留当前选中项、弹窗状态、播放器状态、筛选条件、展示模式等 UI 状态

这说明项目已经逐步摆脱“所有数据都塞进 Pinia”的传统模式。

这类设计的优势是：

- 避免服务端数据在 Store 中重复缓存
- 降低状态同步复杂度
- 让 Query 接管失效和重新拉取
- 让 Store 更聚焦在页面交互层

## 5.3 问题：全局策略虽正确，但项目内执行仍不完全统一

虽然部分模块已经做到 Store UI 化，但整个项目并未完全统一执行这套策略。

目前可见以下混合情况：

- 有的 Store 只管 UI 状态
- 有的 Store 管业务域选择态
- 有的页面以 route 参数为主状态来源
- 有的模块又引入 scoped project store 作为局部真实来源

这说明项目正在探索“全局状态”和“业务域状态”的边界，但尚未形成强一致约定。

## 5.4 风险：可能出现多真实来源并存

例如项目 ID、团队 ID、当前业务上下文等变量，在不同页面中可能来自：

- route params / query
- 全局 project store
- 业务域 scoped store
- 某个局部组件内部状态

如果没有统一约束，长期来看会产生以下问题：

- 状态来源不清晰
- 调试成本上升
- 页面跳转时旧状态残留
- 跨模块联动不可预测

### 建议

应明确：

- 哪些状态是“全局会话态”
- 哪些状态是“业务域局部态”
- 哪些状态必须以路由为单一事实来源
- 哪些状态允许持久化，哪些只能存在内存中

# 六、数据模型与抽象程度审查

## 6.1 优点：已经具备 Adapter 与 Transformer 意识

项目中已经存在：

- API Adapter 层
- Response 统一类型
- Team Transformer 等数据转换器

这说明当前架构已具备对“原始后端结构”和“前端消费结构”进行隔离的意识。

这是后续做领域建模的良好基础。

## 6.2 问题：Transformer 体系尚未制度化

目前数据转换并不是所有业务域都统一遵循的强约束，而是局部存在。

结果表现为：

- 某些接口结果经过转换后再供页面使用
- 某些接口结果则直接透传给页面
- 某些字段兼容逻辑写在组件中
- 某些 fallback 决策写在组件中

这说明数据模型抽象层没有形成稳定的统一出口。

## 6.3 风险：UI 组件直接感知后端结构波动

当页面直接依赖后端 DTO 时，会出现以下问题：

- 后端字段名变更会直接影响 UI
- 同一业务实体在不同页面上出现不同字段读法
- 组件中出现大量 `a ?? b ?? c` 的兼容逻辑
- 展示模型和编辑模型混用

这会让 UI 层逐渐演变为“协议兼容层”，破坏分层。

## 6.4 建议：建立三类模型边界

建议在后续重构中明确三类模型：

### 1）DTO

后端返回结构，用于网络层和基础映射层。

### 2）ViewModel

页面展示结构，用于卡片、列表、图表、详情区等。

### 3）FormModel

表单编辑结构，用于创建、编辑、提交。

通过 Mapper 将 DTO 转为 VM 或 FormModel，可以有效降低页面对后端结构的敏感性。

# 七、缓存策略审查

## 7.1 当前缓存体系现状

项目当前至少存在以下几类缓存机制：

### 1）Vue Query 缓存

负责服务端状态缓存、过期策略和重新拉取。

### 2）HTTP 层缓存

包括：

- 请求去重
- pending request 合并
- TTL 缓存
- LRU 缓存

### 3）表格级缓存

通过 `TableCache` 管理分页、搜索条件和缓存失效策略。

### 4）PWA Runtime Cache

通过 Workbox 对部分 API 或静态资源进行缓存。

从“能力完备性”角度看，项目缓存机制比较丰富。

## 7.2 优点：性能优化意识较强

项目在缓存方面体现出较强的性能治理意识：

- 避免重复请求
- 提升列表切换效率
- 提升首次加载后的交互体验
- 通过 staleTime/gcTime 控制数据新鲜度
- 通过 LRU 防止无界缓存增长

这些都是成熟项目常见的正向特征。

## 7.3 问题：缓存层次偏多，职责边界不够统一

当前最大隐患不是“没有缓存”，而是“缓存层过多而缺乏统一策略”。

### 可能的冲突点：

#### 1）Vue Query 与 HTTP TTL 缓存可能重叠

如果一个 GET 请求同时使用：

- Query staleTime
- HTTP cacheTTL

则数据是否真正过期将变得难以判断。

#### 2）Vue Query 与 HTTP 去重职责可能重叠

Vue Query 对相同 queryKey 的并发请求已具备一定管理能力，HTTP 层再做去重虽然不是错误，但会增加调试复杂度。

#### 3）表格缓存与 Query 缓存可能双重维护

若某个列表页已经由 Query 统一缓存，再叠加自定义 TableCache，可能导致：

- 失效不一致
- 页面刷新行为不直观
- 数据何时更新难以预测

#### 4）PWA 缓存与业务态缓存叠加风险

如果 runtimeCaching 直接缓存用户态业务接口，而没有严格限制场景，可能带来：

- 读取到陈旧业务数据
- 多账号切换后的缓存污染
- 鉴权相关数据不一致

## 7.4 建议：建立缓存分工原则

建议将缓存职责统一为：

### 默认策略

- 服务端业务数据默认只交给 Vue Query 缓存

### HTTP 层保留能力

- 保留并发请求去重
- 仅在少数场景使用 request-level TTL cache

### TableCache 使用条件

- 只用于特殊重型表格组件
- 或非 Query 驱动的数据视图

### PWA 缓存建议

- 以静态资源缓存为主
- 业务 API 缓存需经过白名单评估

# 八、错误处理机制审查

## 8.1 优点：基础设施层错误治理相对成熟

当前 HTTP 层已经实现较完整的错误治理能力，包括：

- 统一错误类型封装
- 状态码转义
- Token 失效处理
- 401 自动刷新与并发保护
- 未授权错误防抖
- 自动重试
- 统一错误提示
- 成功消息提示

这说明基础设施层设计比较成熟，明显优于普通业务前端项目。

## 8.2 问题：页面层仍存在重复错误处理

虽然 HTTP 层已经具备统一错误处理能力，但很多页面和 mutation 逻辑中仍会：

- 再次 try/catch
- 再次 toast
- 再次写失败日志
- 再次定义 UI 失败文案

这样会带来几个问题：

- 重复提示风险
- 相同行为在不同页面实现不一致
- 成功/失败文案分散在组件中
- mutation 与页面交互恢复逻辑耦合过深

## 8.3 问题：缺少明确的错误分层策略

当前错误处理更多是“基础层统一 + 页面各自补一层”，但尚未形成清晰的三层错误体系。

建议明确区分：

### 1）传输错误

网络异常、超时、401、5xx。

### 2）领域错误

例如：

- 项目不存在
- 当前团队无权限
- 当前状态不允许提交审核

### 3）呈现错误

即页面最终以什么方式反馈：

- Toast
- Inline Alert
- Empty State
- Retry Button
- 静默失败

若这三层边界清晰，则组件不必再承担过多错误控制职责。

# 九、数据层与 UI 组件分离程度评估

综合代码现状，当前项目的数据处理逻辑与 UI 分离程度可评估为：

## 9.1 优势部分

### 1）网络请求已显著脱离组件

页面大多数不再直接操作 Axios。

### 2）服务端状态管理已部分标准化

Vue Query 已成为主流方案。

### 3）Store 正在 UI 化

部分业务域已经明确将 Store 收敛为选中态、弹窗态、筛选态等。

### 4）基础设施下沉较充分

认证、缓存、请求治理、错误处理基本集中在底层。

## 9.2 不足部分

### 1）组件仍承担 ViewModel 构造

多接口拼装、派生字段计算、fallback 选择仍频繁出现在页面中。

### 2）组件仍承担业务流程编排

批量删除、批量归档、批量恢复等 mutation orchestration 仍主要在页面层。

### 3）领域模型抽象不稳定

并非所有模块都通过统一 mapper 将 DTO 转为 VM。

### 4）错误策略未完全下沉

组件仍然承担不少错误提示与兜底处理工作。

### 5）缓存策略多层并存

导致数据刷新边界不够透明。

## 9.3 综合判断

当前项目并不是“UI 与数据逻辑混杂严重”的状态，而是属于：

- **基础分层已经形成**
- **关键边界还未完全固化**
- **不同模块成熟度不一致**

因此项目最适合的方向不是推翻重做，而是**沿着现有 Query + UI Store 的方向继续收敛和统一规范**。

# 十、主要改进空间识别

基于本次审查，当前最值得优先改进的空间主要集中在以下几类：

## 10.1 页面级数据聚合逻辑下沉不足

应将：

- 多接口聚合
- 图表数据转换
- 业务指标计算
- 展示字段拼装

从页面组件中抽离到：

- composable
- selector
- domain model hook
- mapper

## 10.2 Query 层缺少统一 key 管理

建议建立 key factory，避免 queryKey 分散、失效策略重复。

## 10.3 Mutation 编排逻辑未统一下沉

应将：

- 批量操作
- 顺序/并发执行策略
- 成功失败反馈策略
- cache invalidation

从页面抽到领域 action 层。

## 10.4 DTO 与 ViewModel 边界不明确

建议禁止页面直接长期依赖后端 DTO 作为展示实体。

## 10.5 缓存分工未完全统一

应重新梳理：

- Query cache
- HTTP cache
- Table cache
- PWA cache

各自的适用边界。

## 10.6 错误处理层次不清晰

建议将错误治理明确划分为：

- 基础设施错误
- 领域错误
- 呈现错误

***

# 十一、数据层进一步分离的实施方案

以下给出一套适合当前项目逐步落地的实施方案。

## 11.1 目标架构

建议将数据层进一步收敛为四层：

### 第一层：基础设施层（Infra）

职责：

- HTTP
- QueryClient
- Storage
- Token
- Retry
- Error Normalization

### 第二层：接口访问层（API）

职责：

- 只定义请求
- 不负责 UI 逻辑
- 不负责数据拼装
- 不负责页面错误文案

### 第三层：领域数据层（Domain）

职责：

- query keys
- query hooks
- mutation hooks
- mappers
- selectors
- actions
- invalidation strategy

### 第四层：表现层（Presentation）

职责：

- 组件渲染
- 用户交互
- 页面布局
- 最终展示反馈

页面层不应再承载大规模数据格式兼容和业务编排逻辑。

***

## 11.2 建议目录结构

建议逐步演进为如下结构：

```text
src/
  domain/
    project/
      api.ts
      keys.ts
```

## 11.3 接口抽象方法建议

### 建议一：保留现有 `src/api/*.ts` 作为基础请求定义

它们可以继续承担：

- endpoint 定义
- 参数传递
- responseType 配置
- 低层请求调用

### 建议二：在领域层建立统一导出入口

例如 `domain/project`：

- `api.ts` 负责重导出项目相关接口
- `queries.ts` 负责项目查询 hook
- `mutations.ts` 负责项目变更 hook
- `actions.ts` 负责复杂流程编排

### 建议三：建立 `keys.ts`

通过 key 工厂统一 queryKey 规范。

***

## 11.4 状态管理优化策略

### 原则一：服务端状态一律优先交给 Vue Query

包括：

- 列表
- 详情
- 统计
- 关系型数据
- 任务状态

### 原则二：Pinia 只保留以下内容

- 当前选中项
- 业务域上下文
- 弹窗开关
- 视图模式
- 表单草稿
- 本地偏好设置
- 极少量跨页面会话态

### 原则三：路由状态作为事实来源的场景必须明确

例如：

- 当前 projectId 如果由 URL 决定，则应尽量以路由为唯一事实来源
- scoped store 仅作为 fallback 或局部缓存，不应与 route 长期双向竞争

***

## 11.5 数据转换与 ViewModel 策略

建议建立以下规范：

### 1）页面禁止直接长期依赖原始 DTO

### 2）图表、卡片、列表项统一返回 VM

### 3）表单编辑统一使用 FormModel

### 4）兼容字段与 fallback 一律放在 mapper / selector 中

例如统计页可抽象出：

- `useSalesOverviewModel(teamId)`
- `useProjectListPageModel(params)`
- `useStoryboardDesignModel(projectId, filters)`

让页面只消费最终可渲染模型。

***

## 11.6 Mutation 流程下沉策略

建议新增一层“领域动作”封装复杂写操作，例如：

- `useProjectBatchActions()`
- `useStoryboardBulkActions()`
- `useTeamMemberActions()`

其职责包括：

- 调用多个 mutation
- 定义顺序/并发策略
- 统一失败收集
- 统一成功反馈
- 统一埋点与日志
- 统一 cache invalidation

这样页面只负责：

- 收集用户输入
- 弹确认框
- 调用 action
- 根据返回结果展示必要 UI

***

## 11.7 缓存策略收敛建议

建议定义统一缓存准则：

### 默认准则

- 服务端数据默认使用 Vue Query 缓存

### HTTP 层

- 保留请求去重
- 慎用 TTL 缓存
- 默认不与 Query staleTime 叠加

### 表格缓存

- 仅用于特殊重型表格
- 不作为常规列表页默认方案

### PWA 缓存

- 业务 API 应审查后按白名单启用
- 优先缓存静态资源而非高频业务接口

***

## 11.8 错误处理策略优化建议

建议建立统一错误分层：

### 基础设施层错误

由 HTTP/Adapter 层负责：

- 网络异常
- 401/403/5xx
- 重试
- token 刷新

### 领域层错误

由 domain 层负责转义，例如：

- “项目不存在”
- “当前团队无权限操作”
- “当前状态不允许提交审核”

### 表现层错误

由页面决定最终展示方式：

- Toast
- Inline Alert
- Empty State
- Retry 按钮
- 静默处理

同时建议统一 mutation 是否默认弹错：

- 背景轮询与静默刷新可关闭全局错误提示
- 用户主动提交操作则保留明确反馈

# 十二、建议优先实施顺序

为了保证改造成本可控，建议按以下顺序推进。

## 第一阶段：规范统一

目标：先统一规则，不急于大规模改代码。

建议完成：

1. 明确 Store / Query / Route 的职责边界
2. 制定 queryKey 工厂规范
3. 制定 DTO / ViewModel / FormModel 规范
4. 制定错误处理分层规范
5. 制定缓存使用白名单原则

## 第二阶段：优先治理高收益页面

建议优先处理以下页面：

- dashboard / statistics 统计页
- project list 项目列表页
- storyboard design 分镜设计页
- 团队成员与分析类页面

这些页面最容易暴露：

- 多接口聚合
- 页面过厚
- mutation 编排分散
- 缓存失效复杂

## 第三阶段：建设领域目录

以 `project`、`statistics`、`storyboard` 为第一批，逐步形成领域层目录。

## 第四阶段：收敛缓存与错误策略

对以下内容进行统一治理：

- 去除不必要的双重缓存
- 统一 mutation 错误提示策略
- 统一列表页刷新策略
- 统一批量操作流程封装方式

# 十三、最终评估

## 13.1 架构成熟度评价

从数据层能力完整度来看，当前项目已经具备较成熟的现代前端数据治理基础。

如果以 10 分制评估：

- **数据层基础设施能力：7.5 / 10**
- **数据层与 UI 解耦程度：6 / 10**

## 13.2 核心判断

当前项目的主要矛盾并不在于“是否引入了正确技术”，而在于：

- 正确的技术方案已经存在
- 但尚未在所有业务域中形成统一、稳定、强约束的分层规范

## 13.3 最重要的改进方向

如果只优先做最关键的几项工作，建议按以下顺序推进：

1. 将统计与看板页的数据拼装逻辑下沉为领域 composable / selector
2. 建立统一 query key factory
3. 将批量 mutation 流程从组件抽离到 domain actions
4. 建立 DTO → ViewModel 映射规范
5. 收敛 Vue Query、HTTP cache、TableCache、PWA cache 的职责边界

# 十四、总结

总体而言，当前 Dreamcraft Astra 前端项目的数据层架构已经具备良好基础，并且已经朝着现代分层架构迈出了关键一步：

- 服务端状态逐步交给 Vue Query
- 本地状态逐步收敛到 Pinia UI Store
- 网络请求治理集中
- 数据流治理能力较强

但要进一步提升代码的：

- 可维护性
- 可测试性
- 可复用性
- 架构一致性

仍需继续推动“页面层瘦身、领域层增厚、模型边界清晰、缓存职责统一、错误策略分层”这五个方向。

建议以后续渐进式演进为主，而非一次性大重构。沿着当前已有基础继续规范化收敛，将是成本最低、收益最高的方案。
