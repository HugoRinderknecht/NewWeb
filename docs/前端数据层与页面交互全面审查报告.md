## 二、数据获取策略分析

### 2.1 TanStack Vue Query 配置评估

**配置代码** (`src/plugins/vue-query.ts`):

```typescript
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      refetchOnWindowFocus: false,
      retry: 1,
      staleTime: 5 * 60 * 1000,  // 5 分钟
      gcTime: 10 * 60 * 1000     // 10 分钟
    }
  }
})
```

**优点**:
- 全局配置了合理的 `staleTime`（5分钟）和 `gcTime`（10分钟），避免频繁请求
- 每个 Query Hook 可独立覆盖配置（如 `useStatsRealtime` 的 `staleTime: 30s`）
- 实时数据查询配置了 `refetchInterval` 自动轮询

**改进建议**:
- `refetchOnWindowFocus: false` 在用户切回页面时可能导致数据陈旧，建议根据业务场景评估是否开启
- 缺少 `networkStatus` 相关配置，可考虑在网络断开时提供更好的用户体验
- 全局 `retry: 1` 对所有查询生效，某些敏感查询（如扣费操作）应单独配置为 `retry: false`

### 2.2 查询 Hook 设计评估

**优点**:
- 每个功能模块有独立的查询文件（如 `statistics.ts`、`project.ts`、`team.ts`）
- 统一导出入口 (`src/api/queries/index.ts`)，方便按需导入
- 使用 `MaybeRefOrGetter` 支持响应式参数，查询键自动跟随依赖变化
- 大量使用 `enabled` 条件控制，防止无效请求（如 `enabled: () => !!toValue(teamId)`）
- 变更操作（Mutation）统一使用 `queryClient.invalidateQueries` 保持缓存一致性

## 三、状态管理方案分析

### 3.1 Pinia Store 设计评估

项目采用 **Pinia** 作为状态管理方案，并配合 **pinia-plugin-persistedstate** 实现持久化。

#### Store 分层策略（"轻量 Store + Query" 模式）

这是该项目的一个显著优点，体现了对现代前端状态管理最佳实践的理解：

| Store 类型 | 示例 | 职责 | 持久化 |
|-----------|------|------|--------|
| **轻量 UI Store** | `team.ts`、`project.ts` | 仅存储 UI 相关状态（当前选中 ID）| sessionStorage |
| **数据 Store** | `project-data.ts` | 复杂 UI 状态（播放器状态、轨道数据）| 无 |
| **持久化 Store** | `user.ts`、`setting.ts` | 用户信息、主题、语言设置等 | sessionStorage / localStorage |
| **服务端数据** | — | 全部通过 Vue Query Hook 获取 | — |

**示例 — `team.ts`**（轻量 Store，仅追踪当前团队 ID）:

```typescript
export const useTeamStore = defineStore('team', () => {
  const currentTeamId = ref<string>('')
  const setCurrentTeamId = (teamId: string) => {
    currentTeamId.value = teamId
  }
  return { currentTeamId, setCurrentTeamId }
}, { persist: false })
```

**示例 — `project-data.ts`**（通过 computed 代理 project store 的 currentProjectId，消除循环依赖）:

```typescript
const projectStore = useProjectStore()
const currentProjectId = computed({
  get: () => projectStore.currentProjectId,
  set: (val: string) => projectStore.setCurrentProject(val)
})
```

**评价**: 这种"轻量 Store + Query"的模式是现代 Vue 应用的最佳实践。服务端数据交给 TanStack Query 管理，Pinia 仅负责 UI 状态，职责划分非常清晰。

### 3.2 持久化策略

**user store** (`persist: { key: 'user', storage: sessionStorage }`):
- 存储：用户信息、访问令牌、刷新令牌、搜索历史、锁屏状态
- 使用 `sessionStorage` 而非 `localStorage`，关闭标签页后自动清除，安全性更好

**setting store** (`persist: { key: 'setting', storage: localStorage, pick: [...] }`):
- 仅持久化用户偏好的配置项（主题、菜单状态、功能开关等）
- 使用 `pick` 白名单精确控制哪些字段持久化，避免敏感数据泄漏

**project store** (`persist: { key: 'project', storage: sessionStorage, pick: ['currentProjectId'] }`):
- 仅持久化当前项目 ID，用户刷新页面后保持上下文

### 3.3 版本化存储键管理

通过 `StorageKeyManager` 实现跨版本数据迁移：

```typescript
getStorageKey(storeId: string, storage: Storage = localStorage): string {
  const currentKey = this.getCurrentVersionKey(storeId)
  if (this.hasCurrentVersionData(currentKey, storage)) return currentKey
  const existingKey = this.findExistingKey(storeId, storage)
  if (existingKey) this.migrateData(existingKey, currentKey, storage)
  return currentKey
}
```

**评价**: 版本化存储键管理确保了应用升级时旧版本数据能平滑迁移到新版本，避免了用户数据丢失的问题。这是生产级应用的重要实践。

### 3.4 问题与改进建议

1. **token 未自动刷新**: `fetchRefreshToken` 函数已定义，但 HTTP 层没有实现自动刷新机制。当 `accessToken` 过期时，只能通过 401 错误触发登出，而不是静默刷新 token。建议实现 Token 自动刷新拦截器。
2. **Pinia Store 缺乏 TypeScript 严格类型**: 部分 Store 的 state 类型通过 `ref` 推断，缺乏显式 interface 声明，可维护性有提升空间。
3. **部分 computed 永远返回空字符串**: `useProjectStore` 和 `useTeamStore` 的 `currentProjectName`/`currentTeamName` computed 直接返回 `''`，名从服务端获取但未实现联动。建议通过 watch + queryClient 获取。

## 四、缓存机制分析

### 4.1 多层缓存架构

```
┌─────────────────────────────────────┐
│  Vue Query 缓存（内存）              │
│  staleTime: 5min / gcTime: 10min  │
│  支持查询键粒度的缓存管理             │
├─────────────────────────────────────┤
│  HTTP 层响应缓存（内存 Map）         │
│  cacheTTL 配置，TTL 过期自动失效     │
│  适用于不经过 Vue Query 的请求        │
├─────────────────────────────────────┤
│  监控器指标缓存（DataFlowMonitor）    │
│  1 秒内重复计算直接返回缓存结果        │
├─────────────────────────────────────┤
│  持久化缓存（localStorage / sessionStorage）│
│  StorageKeyManager 版本化管理        │
└─────────────────────────────────────┘
```

### 4.2 HTTP 层缓存实现

```typescript
// 缓存读取
if (config.cacheTTL && config.cacheTTL > 0) {
  const key = getRequestKey(config)
  const cached = responseCache.get(key)
  if (cached && Date.now() - cached.timestamp < config.cacheTTL) {
    return cached.data as T
  }
}
// 缓存写入
if (config.cacheTTL && config.cacheTTL > 0) {
  const key = getRequestKey(config)
  responseCache.set(key, { data: result, timestamp: Date.now() })
}
```

**评价**: HTTP 层缓存为不过 Vue Query 的请求（如 SSE 连接）提供了兜底缓存方案。但该缓存是内存缓存，刷新页面后丢失，且 `cacheTTL` 在实际 API 函数中未使用到。

### 4.3 请求去重

```typescript
const pendingRequests = new Map<string, Promise<any>>()
// GET 请求自动去重，同一 key 的并发请求复用同一个 Promise
if (enableDedup) {
  const existing = pendingRequests.get(key)
  if (existing) return existing as Promise<T>
  const promise = _doRequest<T>(config).finally(() => {
    pendingRequests.delete(key)
  })
  pendingRequests.set(key, promise)
  return promise
}
```

**评价**: 请求去重机制避免了页面快速操作触发的并发请求风暴，特别是在组件频繁挂载/卸载的场景下非常有用。

### 4.4 问题与改进建议

1. **HTTP 层 `cacheTTL` 未被使用**: HTTP 缓存逻辑存在但 `cacheTTL` 参数从未在任何 API 函数中传入，导致 HTTP 层缓存实际上不生效。所有缓存都依赖 Vue Query 层。
2. **缓存无大小限制**: HTTP 层 `responseCache` 是无限制的 Map，长时间运行可能导致内存泄漏。应实现 LRU 淘汰策略或设置最大条目数。
3. **缺乏缓存预热机制**: 对于首页高频访问的数据（如 dashboard、统计数据），没有预加载策略，用户首次访问需要等待加载。
4. **缓存失效策略不够灵活**: 当前 Vue Query 依赖 `invalidateQueries` 手动失效，可考虑增加基于时间的自动失效配置。

## 五、错误处理流程分析

### 5.1 统一错误处理架构

```
Axios 响应拦截器
  ├─ code === 200  → 直接返回响应
  ├─ code === 401  → handleUnauthorizedError() → 登出
  └─ 其他 code     → 抛出 HttpError
        │
        ▼
handleError(error: AxiosError)
  ├─ ERR_CANCELED  → "请求已取消"
  ├─ 无 response   → "网络错误，请检查网络连接"
  └─ HTTP 状态码   → getErrorMessage() → 映射错误文本
        │
        ▼
showError(error: HttpError)
  ├─ ElMessage.error() → UI 提示
  └─ console.error()    → 日志记录
```

### 5.2 HttpError 类设计

```typescript
export class HttpError extends Error {
  public readonly code: number
  public readonly data?: unknown
  public readonly timestamp: string
  public readonly url?: string
  public readonly method?: string

  public toLogData(): ErrorLogData { ... }
}
```

**评价**: `HttpError` 封装了完整的错误上下文（状态码、附加数据、时间戳、请求URL/方法），通过 `toLogData()` 方法方便日志收集和上报，符合生产级错误处理标准。

### 5.3 业务码枚举体系

`src/utils/http/status.ts` 定义了 **400+ 个业务码**，覆盖：
- 认证错误 (1001-1017)
- 团队管理错误 (2001-2024)
- 项目管理错误 (3001-3018)
- 分镜管理错误 (4001-4018)
- 审核任务错误 (5001-5020)
- 资产管理错误 (6001-6115)
- 通知系统错误 (9001-9034)
- Dify 工作流错误 (9401-9429)

```typescript
export function getBusinessErrorMessage(code: number): string {
  if (code === BusinessCode.SUCCESS) return '操作成功'
  if (code >= 1001 && code <= 1017) return '认证错误'
  if (code >= 2001 && code <= 2024) return '团队管理错误'
  // ...
  return '未知错误'
}
```

**评价**: 业务码枚举体系非常完善，涵盖了所有主要业务模块的错误类型，为前端提供了精确的错误识别和用户友好提示的基础。

### 5.4 401 错误防抖机制

```typescript
let isUnauthorizedErrorShown = false
let unauthorizedTimer: NodeJS.Timeout | null = null

function handleUnauthorizedError(message?: string): never {
  if (!isUnauthorizedErrorShown) {
    isUnauthorizedErrorShown = true
    logOut()
    unauthorizedTimer = setTimeout(resetUnauthorizedError, UNAUTHORIZED_DEBOUNCE_TIME)
    showError(error, true)
    throw error
  }
  throw error
}
```

**评价**: 401 错误防抖机制（3秒内只触发一次登出）有效避免了并发请求导致重复登出的问题。

### 5.5 重试机制

```typescript
async function retryRequest<T>(config, retries = MAX_RETRIES): Promise<T> {
  try {
    return await request<T>(config)
  } catch (error) {
    if (retries > 0 && error instanceof HttpError && shouldRetry(error.code)) {
      await delay(RETRY_DELAY)
      return retryRequest<T>(config, retries - 1)
    }
    throw error
  }
}
```

**评价**: 自动重试机制覆盖了请求超时、服务器内部错误、网关错误等瞬时故障，重试次数（1次）和延迟（1秒）的配置合理。

### 5.6 问题与改进建议

1. **缺少全局错误边界**: 整个应用没有全局错误边界组件，组件级别的错误可能导致白屏。建议在根组件添加错误边界。
2. **业务码处理分散**: `getBusinessErrorMessage` 通过范围判断确定错误类别，但相同范围内的不同错误码返回相同消息，粒度不够细致。实际使用中可能需要更精确的错误提示。
3. **错误日志上报机制缺失**: 错误通过 `console.error` 输出但没有上报到监控系统（如 Sentry）。建议接入错误监控服务。
4. **SSE 错误处理独立**: SSE 连接使用原生 `fetch` + 手动错误处理，与 Axios 层错误处理不一致，缺少统一性。

### 6.3 DataFlowMonitor 指标采集

`DataFlowMonitor` 提供了流转指标采集和告警功能：
- **指标类型**: 流转次数、失败次数、平均耗时、P95 耗时、吞吐量、错误率
- **告警规则**: 高错误率（>50%）、慢流转（>3s）、P95 高延迟（>10s）
- **冷却机制**: 避免告警风暴（高错误率冷却30s，慢流转冷却60s）

**评价**: 监控体系完整，具备生产级别的可观测性基础。

### 6.4 问题与改进建议

1. **转换器未广泛使用**: `DataTransformerManager` 定义了完整的转换框架，但实际业务代码（如 `sales-overview.vue`）直接通过 `computed` 进行数据提取，没有使用内置转换器。转换器框架的使用率偏低。
2. **缺乏 DTO 类型映射**: 没有在 API 层实现数据从后端 DTO 到前端领域模型的转换逻辑，当前类型直接使用后端返回的 `Api.*` 命名空间类型，缺乏显式的转换层。
3. **转换器注册在全局单例**: `dataTransformerManager` 是全局实例，转换器在模块初始化时注册。如果需要为不同模块注册不同转换器集，缺乏隔离机制。
4. **DataFlowMonitor 未被实际调用**: `recordTransfer()` 方法定义了但没有在数据获取流程中被调用，监控功能目前停留在框架层面，未实际生效。

## 七、API 交互模式分析

### 7.1 适配器模式

```typescript
// 接口定义
export interface IApiAdapter {
  request<T>(config: RequestConfig): Promise<T>
  get<T>(url, params?, config?): Promise<T>
  post<T>(url, data?, config?): Promise<T>
  put<T>(url, data?, config?): Promise<T>
  del<T>(url, params?, config?): Promise<T>
  patch<T>(url, data?, config?): Promise<T>
}

// HTTP 适配器实现
export class HttpAdapter implements IApiAdapter {
  async request<T>(config: RequestConfig): Promise<T> {
    return request.request<T>({ ...config })
  }
}
```

**评价**: 适配器模式实现了 `IApiAdapter` 接口解耦，当前仅使用 `HttpAdapter`。这种设计为未来切换到其他 HTTP 客户端（如原生 fetch、ky）提供了灵活性。

### 7.2 API 函数类型化

```typescript
export function fetchGetTrends(
  teamId: string,
  params?: Omit<Api.Statistics.TrendParams, 'teamId'>
) {
  return getApiAdapter().get<Api.Statistics.TrendData>(
    `/api/statistics/teams/${teamId}/trends`,
    params
  )
}
```

**优点**:
- 所有 API 函数都有完整的 TypeScript 类型声明
- 请求参数和响应数据均类型化，IDE 自动完成度高
- URL 模板参数（如 `{teamId}`）在类型层面无校验，运行时由模板字符串展开

### 7.4 请求参数处理

- **GET 请求**: 参数通过 `params` 传递，axios 自动序列化为查询字符串
- **POST/PUT 请求**: 参数通过 `data` 传递，Content-Type 默认为 `application/json`
- **FormData 支持**: HTTP 拦截器自动识别 FormData，跳过 Content-Type 设置
- **参数转换**: 部分场景（如 POST 参数放入 body 而非 query）有自动转换逻辑

```typescript
// HTTP 层自动将 POST/PUT 的 params 移入 data
if (['POST', 'PUT'].includes(config.method) && config.params && !config.data) {
  config.data = config.params
  config.params = undefined
}
```

### 7.5 响应数据解析

```typescript
// 统一响应格式
interface BaseResponse<T = unknown> {
  code: number       // 业务状态码
  message: string    // 消息文本
  msg?: string       // 备用消息字段
  data: T            // 响应数据
  timestamp?: number // 时间戳
}
```

**问题**: `message` 和 `msg` 两个字段并存需要兼容处理，当前代码使用 `message || msg` 作为兜底，这种双重字段设计是历史遗留问题，建议与后端对齐统一使用一个字段。

### 7.6 问题与改进建议

1. **缺失 API Mock 机制**: 项目没有配置 MSW (Mock Service Worker) 或其他 API Mock 方案，前端开发和测试依赖真实后端。
2. **URL 参数类型不安全**: API 路径参数（如 `/api/statistics/teams/${teamId}/trends`）是字符串模板，TypeScript 不会校验参数是否存在或格式正确，建议封装成类型安全的 API 路由函数。
3. **缺少 API 版本管理**: 所有 API 路径直接使用 `/api/xxx`，没有版本前缀（如 `/api/v1/xxx`）。未来 API 演进时可能面临兼容性问题。
4. **API 函数缺少请求取消**: 虽然底层支持 `AbortSignal`，但 API 函数没有暴露取消机制（`useQuery` 自带取消，但直接调用 API 函数则不能取消）。

# 第二部分：页面组件数据交互深度审查

## 八、数据请求发起时机与触发条件分析

### 8.1 触发模式分类

经过对 17 个核心页面组件的全面审查，发现以下几种数据请求触发模式：

#### 模式 A：隐式挂载触发（最常见）

```typescript
// dashboard/console/index.vue
// Hook 在 setup 中直接调用，请求在组件挂载时自动发起
const { data: teamsData } = useMyTeams()

watch(teamsData, () => {
  checkOnboardingStatus()
})
```

**问题**: `watch` 触发依赖数据加载时序，如果数据在 watch 注册前就已返回，回调不会执行。这是典型的**时序竞态风险**。

#### 模式 B：Computed 响应式触发（推荐）

```typescript
// sales-overview.vue
// computed ref 作为查询参数，参数变化时自动重新请求
const trendParams = computed(() => ({
  eventType: 'credits',
  granularity: 'day',
  metrics: ['credits']
}))
const { data: trendData } = useStatsTrends(teamId, trendParams)
```

**评价**: 这是最推荐的模式，参数驱动型查询，响应式链路清晰。

#### 模式 C：Watch + 手动 refetch（少数场景使用）

```typescript
// script/write/index.vue
const loadScriptDetail = async (id: string) => {
  try {
    const result = await scriptDetailQuery.refetch()
    // ...
  }
}
```

**问题**: 手动 `refetch()` 调用混合了 TanStack Query 与直接 API 调用两种模式，逻辑不一致。

#### 模式 D：Manual invalidateQueries 刷新（通知模块）

```typescript
// notice/site/index.vue
const loadNoticeList = async () => {
  searchKeyword.value = undefined
  await queryClient.invalidateQueries({ queryKey: ['notifications', 'list'] })
}
```

**评价**: 通过手动使缓存失效来触发刷新，适合用户主动刷新场景。

### 8.2 触发条件评估

| 组件 | 触发类型 | enabled 控制 | 评价 |
|------|---------|-------------|------|
| sales-overview | Computed 参数 | ✅ 自动 | 良好 |
| card-list | 隐式挂载 | — | 一般（无条件触发）|
| dynamic-stats | 隐式挂载 | — | 一般（无条件触发）|
| project/list | Computed 参数 | ✅ 自动 | 良好 |
| storyboard/design | Computed 参数 + watch error | ✅ 完整 | 优秀 |
| script/write | 手动 refetch | — | 较差 |
| notice/site | 手动 invalidate | — | 一般 |
| team/members | Computed 参数 | ✅ 自动 | 良好 |

### 8.3 问题与改进建议

1. **Watch-only 触发存在竞态风险**: `dashboard/console/index.vue` 中的 `checkOnboardingStatus()` 仅通过 `watch` 触发，如果 `teamsData` 在 watch 注册前已返回，回调不会执行。应增加 `onMounted` 中的主动检查。
2. **隐式挂载无 enabled 控制**: 多数 Dashboard 模块直接调用 Hook 无条件触发请求，虽然不一定会发请求（底层 `enabled` 由 `teamId` 等参数控制），但代码意图不清晰。
3. **手动 refetch 模式不推荐**: `script/write/index.vue` 中的 `refetch()` 手动调用模式混用了 Query 与直接 API 逻辑，应统一为响应式参数驱动。

## 十、数据响应处理与异常机制分析

### 10.1 响应数据处理模式

#### 标准处理（多数组件）

```typescript
// 大多数组件使用 computed 从 .value 中提取数据
const projectList = computed(() => listResult.value?.records ?? [])
const totalFromApi = computed(() => listResult.value?.total ?? 0)

watch(totalFromApi, (val) => {
  pagination.total = val
})
```

**评价**: 良好的链式处理——从 API 响应 → computed 转换 → 分页状态更新，层次清晰。

#### 数据转换工具函数

```typescript
// team/members/index.vue
const memberList = computed(() => transformTeamMemberList(memberData.value?.records))
```

**评价**: 独立的数据转换函数（`transformTeamMemberList`、`transformRoleOptions`）将业务逻辑从组件中分离，保持组件简洁。

#### 反模式：Watch + Reactive Array 手动操作

```typescript
// recent-project.vue（反模式）
const tableData = reactive<ProjectTableItem[]>([])

watch(projectData, (res) => {
  if (res?.records) {
    tableData.splice(
      0,
      tableData.length,
      ...res.records.map((item: any, index: number) => ({
        // ...
      }))
    )
    addAnimation()
  }
})
```

**问题**:
- 用 `watch` + `reactive` + `splice` 操作数组，而非直接用 computed 派生
- 动画逻辑（`addAnimation()`）与数据获取耦合
- `as any` 类型绕过导致运行时风险

### 10.2 错误处理模式

#### 模式 A：未处理（大多数组件）

```typescript
// sales-overview.vue, card-list.vue, dynamic-stats.vue
// error 变量完全未提取或未使用
const { data: trendData } = useStatsTrends(teamId, trendParams)
// error 状态被忽略
```

**影响**: 请求失败时组件不显示任何错误提示，用户体验极差。

#### 模式 B：特定错误码处理（最佳实践）

```typescript
// storyboard/design/index.vue
const { data: listResult, isLoading, error, refetch } = useStoryboardList(projectId, searchParams)

watch(error, (err) => {
  const code = (err as any)?.code
  if (code === 3001 && projectStore.currentProjectId) {
    projectStore.clearCurrentProject()
  }
})
```

**评价**: 这是项目中错误处理的最佳实践——监听 `error` 状态，对特定业务码（如项目不存在 3001）做清除当前项目等业务补偿动作。

#### 模式 C：Query Client 手动捕获

```typescript
// notice/site/index.vue
const handleGetDetail = async (id: string) => {
  try {
    return await queryClient.fetchQuery({
      queryKey: ['notifications', 'detail', id],

  } catch {
    return null
  }
}
```

**评价**: 通过 `queryClient.fetchQuery` 实现带缓存的查询，catch 块返回 null 是合理的降级处理。

### 10.3 异常处理问题汇总

| # | 严重程度 | 组件 | 问题描述 |
|---|---------|------|---------|
| E1 | 高 | 大多数组件 | `error` 状态未提取或未使用，失败无反馈 |
| E2 | 高 | latest-notice.vue | Mutation（标记已读）无 `onError` 处理，失败无提示 |
| E3 | 中 | script/write/index.vue | 混合 TanStack Query + 直接 API 调用，错误处理路径不统一 |
| E4 | 中 | review/pending/index.vue | 批量审批仅处理第一个项，部分失败无提示 |

**评价**: 全局成功消息提示统一在 HTTP 层处理，避免了每个组件单独处理。但 `showSuccessMessage` 默认关闭（`showSuccessMessage?: boolean`），需要显式传入才生效，实际使用率可能偏低。

### 11.2 Mutation 缓存失效策略

#### 良好实践：精确失效

```typescript
// project.ts - 精确失效相关查询
onSuccess: (_data, variables) => {
  queryClient.invalidateQueries({ queryKey: [QUERY_KEY] })
  queryClient.invalidateQueries({ queryKey: [QUERY_KEY, 'detail', variables.projectId] })
}
```

#### 问题：过度宽泛的失效

```typescript
// editor.ts - 所有 editor 查询同时失效

}
```

**问题**: 剪辑项目列表的更新会同时刷新其他不相关剪辑项目的缓存，增加不必要的网络请求。

### 11.3 双缓存架构（useTable）

`useTable` 实现了一套自建的 `TableCache` + TanStack Query 的双缓存方案：

```typescript
// useTable.ts
// 模式1：自建 TableCache（当无 queryKey 时）
const cache = new TableCache(cacheTime, strategy)  // CLEAR_ALL / CLEAR_CURRENT 等策略

// 模式2：TanStack Query 后端（当有 queryKey 时）
const response = await qc.fetchQuery({
  queryKey: [...queryKey, requestParams],
  queryFn: async () => await apiFn(requestParams),
  staleTime: cacheTime
})
```

**评价**: 双缓存设计兼顾了灵活性（自建缓存）与健壮性（TanStack 缓存），是复杂表格数据管理的优秀方案。

| 场景 | 缓存有效性 | 说明 |
|------|-----------|------|

| 分页切换 | ✅ 有效 | `searchParams` 中 pagination 变化产生新键 |
| 筛选条件变化 | ✅ 有效 | computed 参数驱动，条件变化重新请求 |
| 用户在多个标签页操作同一数据 | ⚠️ 部分有效 | Pinia 状态跨标签共享，但 Vue Query 缓存按标签页隔离 |
| 表单自动保存 | ⚠️ 需手动失效 | `script/write` 的 autoSave mutation 未配置缓存失效 |
| 乐观更新 | ❌ 未实现 | 标记已读等操作直接等待服务端返回，未做乐观 UI 更新 |

## 十二、数据层接口设计与组件交互一致性分析

### 12.1 接口设计规范性

#### 良好实践：统一 BaseResponse 包装

```typescript
interface BaseResponse<T = unknown> {
  code: number
  message: string
  msg?: string
  data: T
  timestamp?: number
}
```

所有 API 响应均通过统一格式包装，前端可依赖 `code === 200` 判断成功。

#### 问题：响应字段不一致

分页响应在不同接口中存在字段名差异：
- `records` / `list` / `items` 均可表示数据列表
- `total` / `count` 均可表示总数
- `current` / `page` 均可表示当前页
- `size` / `pageSize` 均可表示页大小

`DataTransformerManager` 的 `builtin:pagination-response` 转换器已处理这一差异，但使用率低。

### 12.2 Query 键设计规范性

```typescript
// 规范的分层查询键
queryKey: ['statistics', 'trends', teamId, params]      // 统计数据 - 趋势 - 团队ID - 参数
queryKey: ['projects', 'detail', projectId]             // 项目 - 详情 - 项目ID
queryKey: ['teams', 'members', teamId, params]         // 团队 - 成员 - 团队ID - 参数
queryKey: ['notifications', 'detail', id]              // 通知 - 详情 - 通知ID
```

**评价**: 查询键遵循 `[模块, 实体, 标识符, 参数]` 四层结构，命名一致性好。

### 12.3 组件与数据层交互一致性

| 交互模式 | 一致性 | 说明 |
|---------|--------|------|
| 组件 → Query Hook → API | ✅ 一致 | 大多数组件遵循此链路 |
| 组件 → useTable → API | ✅ 一致 | 表格数据通过 useTable 封装 |
| 组件 → useTable (queryKey) → TanStack | ✅ 一致 | useTable 可选使用 TanStack 缓存 |
| 组件 → queryClient.fetchQuery | ⚠️ 混合 | 仅 notice 模块使用，与主流模式不同 |
| 组件 → 直接 API 调用 | ❌ 不一致 | script/write 混合模式 |

### 12.4 问题与改进建议

1. **响应类型不一致**: 部分 query 返回 `null` 表示空，部分返回 `[]` 表示空，消费者需要同时处理两种情况。建议统一约定：列表查询返回 `[]`，单个数据查询返回 `null`。
2. **API 函数文件归属混乱**: `fetchGetAiProcessStatus` 定义在 `script.ts` 而非 `ai-process.ts`，`fetchGetAiProcessDetail` 重复定义在不同文件。文件归属应与 Query 层对应。
3. **组件直接访问 queryClient**: `notice/site/index.vue` 中 `queryClient.fetchQuery` 和 `queryClient.invalidateQueries` 直接暴露给组件，增加了组件与框架的耦合度。应在 Query Hook 层封装这些操作。

## 十三、数据加载状态与用户体验优化分析

### 13.1 加载状态展示模式

#### 模式 A：完全缺失（最常见）

#### 模式 B：提取但未使用


## 十四、Hook 层与 Store 层交互分析

### 14.1 useTable 双重架构

`useTable` 是项目中最复杂的数据获取 Hook，提供了两套数据获取机制：

```
┌─────────────────────────────────────────────┐
│              useTable Hook                  │
├─────────────────────────────────────────────┤
│  模式 A: 自建 TableCache                    │
│    - TableCache 类管理内存缓存               │
│    - CacheInvalidationStrategy 枚举控制失效   │
│    - 定时清理 (cacheTime/2 间隔)            │
├─────────────────────────────────────────────┤
│  模式 B: TanStack Query 后端                │
│    - queryKey 传入时激活                     │
│    - 缓存键 = [baseKey, requestParams]      │
│    - 通过 invalidateQueries 失效            │
└─────────────────────────────────────────────┘
```

**AbortController 取消**: 发起新请求前自动取消 in-flight 请求，防止竞态条件。

### 14.2 加载状态机

`useTable` 实现了四态加载机：

```typescript
type LoadingState = 'idle' | 'loading' | 'success' | 'error'
const loadingState = ref<LoadingState>('idle')
const loading = computed(() => loadingState.value === 'loading')
const error = ref<TableError | null>(null)
```

**评价**: 四态机比二元 `isLoading` 更精确，能区分"初始空闲"、"加载中"、"成功"、"出错"四种状态，UI 可以据此做精确分支。

### 14.3 Pinia Store 与 Query 的协作模式

```
┌─────────────────────────────────────────────┐
│  Pinia Stores（UI 状态，跨组件共享）          │
│  - notification.ts: unreadCount (sessionStorage)│
│  - review.ts: pendingCount (sessionStorage)    │
│  - worktab.ts: opened tabs (localStorage)      │
├─────────────────────────────────────────────┤
│  Vue Query Hooks（服务端数据）               │
│  - useNotificationList → notificationData     │
│  - usePendingReviewCount → pendingCount        │
├─────────────────────────────────────────────┤
│  数据流向                                    │
│  Query data → computed → template            │
│  Query data → store.setXxx() → 跨组件共享     │
└─────────────────────────────────────────────┘
```

**评价**: Pinia Store 与 Vue Query 的协作模式设计合理——Query 负责获取数据，Store 负责跨组件共享 UI 状态（如未读数徽章、待审数徽章）。

### 14.4 乐观更新缺失

当前没有任何 mutation 实现乐观更新（Optimistic Update）。例如标记通知已读：

```typescript
// latest-notice.vue - 当前实现
const handleViewDetail = (item: NoticeItem) => {
  markAsReadMutation.mutate(String(item.id))
  // 无乐观更新，已读状态需等服务端返回
}
```

**建议**: 对于 UI 反馈要求高的操作（标记已读、审批操作），应实现乐观更新：

```typescript
// 乐观更新示例
onMutate: async (variables) => {
  await queryClient.cancelQueries({ queryKey: ['notifications'] })
  const previous = queryClient.getQueryData(['notifications'])
  queryClient.setQueryData(['notifications'], (old) =>
    old.map(item => item.id === variables.id ? { ...item, read: true } : item)
  )
  return { previous }
},
onError: (err, variables, context) => {
  queryClient.setQueryData(['notifications'], context.previous)  // 回滚
}
```

## 十五、Vue Query Hook 层深度问题分析

### 15.1 enabled 条件问题

#### 高危：useDataHistoryList 缺少 enabled

```typescript
// data-history.ts
export function useDataHistoryList(params?) {
  return useQuery({
    queryKey: [QUERY_KEY, 'list', params],
    queryFn: async () => {
      const res = await fetchGetDataHistoryList(toValue(params)!)  // 非空断言！
      return res ?? []
    }
    // ❌ 缺少 enabled 检查
  })
}
```

**风险**: 当 `params` 为 `undefined` 时，API 调用被迫使用非空断言绕过类型检查，后端可能返回错误。

#### 中危：useAiProcessHistory 双重检查导致响应延迟

```typescript
// ai-process.ts
enabled: () => {
  const p = toValue(params)
  return !!(p?.projectId && p?.type && p?.businessId)
},
queryFn: async () => {
  const p = toValue(params)
  if (!p?.projectId || !p?.type || !p?.businessId) return []  // 重复检查
  // ...
}
```

**问题**: `enabled` 和 `queryFn` 都检查了 params，但 `enabled` 中的 `toValue(params)` 与 `queryFn` 中的 `toValue(params)` 可能在不同时机求值，存在不一致风险。

### 15.2 Mutation 缓存失效问题

#### 中危：useDeleteEpisode 缺少详情失效

```typescript
// script.ts
onSuccess: () => {
  if (variables.projectId) {
    queryClient.invalidateQueries({ queryKey: [QUERY_KEY, 'episodes', variables.projectId] })
  }
  // ❌ 缺少：[QUERY_KEY, 'episode', variables.scriptId, variables.episodeId]
}
```

#### 中危：editor.ts 中多处过度失效

```typescript
// editor.ts - 多个 mutation 都使用 { queryKey: [QUERY_KEY] } 宽泛失效
useReorderSegments
useAddSegment
useDeleteSegment
useUpdateSegment
```

**问题**: 所有剪辑片段操作都使整个 editor 模块缓存失效，可能导致其他正在编辑的内容被意外刷新。

### 15.3 空状态返回不一致

| Query | 空状态返回 | 文件 |
|-------|-----------|------|
| useScriptList | `null` | script.ts |
| useProjectEpisodes | `[]` | project.ts |
| useStoryboardList | `null` | storyboard.ts |
| useStoryboardVersions | `[]` | storyboard.ts |
| useDataHistoryList | `[]` | data-history.ts |

**影响**: 组件中需要同时处理 `null` 和 `[]` 两种"无数据"情况，增加条件判断代码量。

### 15.4 Mutation 缺乏 onError 处理

大多数 mutation 没有 `onError` 回调：

```typescript
// script.ts - 典型 mutation
export function useCreateScript() {
  return useMutation({
    mutationFn: (payload) => fetchCreateScript(...),
    onSuccess: () => {
      queryClient.invalidateQueries(...)
    }
    // ❌ 缺少 onError
  })
}
```

**影响**: API 失败时错误仅通过 `ElMessage.error()` 显示，没有机会做业务层面的错误补偿（如表单重置、回滚等）。

## 十九、结论

Dreamcraft Astra 前端数据层架构设计**达到了现代前端数据层设计的优秀标准**，在以下几个方面表现突出：

1. **分层清晰**: 从组件 → Query Hook → API 函数 → 适配器 → HTTP 层，层次分明，职责单一。
2. **类型安全**: 全链路 TypeScript 类型化，API 函数、请求参数、响应数据均有类型约束。
3. **最佳实践**: "轻量 Store + Query" 模式是 Vue 3 + TanStack Query 的推荐实践，避免了状态管理过度设计。
4. **缓存策略**: Vue Query 缓存配置合理，useTable 双缓存架构设计出色，去重机制有效，持久化设计完善。
5. **错误处理**: 统一的 `HttpError` 类 + 业务码枚举 + 401 防抖 + 自动重试，构成了完整的错误处理体系。
6. **可观测性**: `DataFlowMonitor` 和 `DataTransformerManager` 提供了监控和转换的基础设施（虽未完全激活）。

### 页面组件交互层面的主要问题

经过对 17 个核心页面组件的深度审查，发现**加载状态 UI 缺失是最普遍的问题**（14/17 组件），其次是**错误处理不完善**（15/17 组件）。这两个问题直接影响用户对应用稳定性和专业性的感知。

### 改进优先级建议

按照 **稳定性 → 可维护性 → 体验** 的优先级，建议按以下顺序推进改进：

1. **阶段一（稳定性）**: 修复 `useDataHistoryList` enabled 缺失、添加 Token 自动刷新、实现全局错误边界
2. **阶段二（一致性）**: 统一空状态返回规范、为所有 mutation 添加 onError、完善精确缓存失效
3. **阶段三（体验）**: 统一加载骨架屏实现、为 sales-overview 等图表组件添加空状态提示
