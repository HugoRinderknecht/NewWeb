## 0. 重要前置说明

OpenAPI 文档 `docs/项目管理/api.json` 中的 `components.schemas` **只包含请求体类型**(如 `ProjectCreateRequest`, `ProjectUpdateRequest`), **并未展开**返回值类型 `ProjectVO`, `ProjectDetailVO`, `ProjectMemberVO`, `ProjectReviewConfigVO`, `ProjectConfigVO`, `PageResultProjectVO`, `PageResultProjectMemberVO`, `CoverUploadResponse`。

这些类型仅以 `$ref` 形式被引用,但目标 schema 缺失。因此本报告中"以 OpenAPI 为准"的判断,大量字段名是从接口 `description` 文本里推断 + 前端实际使用方式佐证而来。 **建议产品/后端同学补全 OpenAPI 中这些 VO 的 schema 定义**,以便后续自动生成类型。

**OpenAPI 定义** (`ProjectReviewConfigUpdateRequest` 已展开):

  "video": "boolean" // 视频审核

**冲突点**:

| 枚举 | admin / member / viewer | admin / director / storyboard / art / video / audio / edit |

**OpenAPI 来源**:

- `ProjectMemberAddRequest.role.pattern` = `^(admin\|director\|storyboard\|art\|video\|audio\|edit)$`
- 描述: "成员角色组编码: admin/director/storyboard/art/video/audio/edit"

⚠️ **额外发现**: OpenAPI 还提到一个旧的描述"修改成员角色...角色:admin-管理员/member-成员/viewer-观察者"(第 494 行), 这与 `ProjectMemberAddRequest` 的 pattern 冲突。**这是 OpenAPI 文档本身的内部矛盾,需要后端同学确认到底以哪个为准。**

### D10. `GET /api/projects` 查询参数风格不一致

**OpenAPI 定义**: `query` 参数引用了 `ProjectQueryRequest` 整对象(单一参数,但是 `in: query`)。

**前端实现** (`fetchGetProjectList`): 直接传对象给 axios 的 `params`,被序列化为 `?page=&pageSize=&keyword=&status=...` 这种平铺 query string。

**实际情况**: Spring Boot 的 `@ModelAttribute`/`@Valid` 一般都接受平铺的 query string,前后端约定通常一致。但 OpenAPI 中标注为 `required: true` 的 `query` 对象参数,某些代码生成器可能会期望传 `?query={...}`。

**建议**: 保持现状(经验上一致),但首次联调时**重点验证此接口**。如果失败再调整。

## 3. 视图层(views/project)与 API 的"自描述"差异

除了 API 层差异外,view 层在数据映射上也存在一些隐患:

### V1. `views/project/list/index.vue`

- 已正确接入真实 API ✓
- `filteredList` 在 `pagedList` 之外又做了一次本地过滤+排序+分页, 与后端的 `keyword/status/sortField/sortOrder/page/pageSize` 重复,造成"先后端分页拿一页,前端再过滤再分页"的混乱。 **建议**: 删除本地过滤,完全交给后端。

### V2. `views/project/edit/index.vue`

- 跨调用 5 个模块(project/script/storyboard/video/asset),全部 onMounted 一次性串行加载,无 loading 进度; 失败仅 ElMessage,无 retry。
- `mapApiStatus` 把后端的 0/1/2/3 状态做了一次冗余的"再校验",其实只需 `Number(data.status)`。
- `loadProjectConfig` 中调用了**两个独立**的接口 `fetchGetProjectConfig` + `fetchGetReviewConfig`, 各自 try/catch 静默吞错,体验不可控。

### V3. `views/project/episodes/index.vue`

- `handleShotReorder`、`handleShotSubmit`、`handleDeleteShot` 全部仅做**本地状态修改**, 并未调用任何后端接口持久化。这是一个**功能性缺陷**(因为分镜模块 API 在另一份文档,本次仅检查项目管理)。
- 与统一改造无关,但建议在 TODO 中标记。

### V4. `views/project/member/index.vue`

- "停用/启用"按钮的 handleDisable/handleEnable 仅改本地 state,未调任何接口(已知,见 D7)。
- `filteredMembers` 在 API 已支持 `keyword` 的情况下,前端又用 `searchQuery` 做了一次过滤,与 V1 一致。

### V5. `views/project/scripts/index.vue`

- 已接入 script 模块 API ✓
- `episodeCount`、`author`、`updateTime` 这几个字段后端 `ScriptVO` 是否返回需要核对(在剧本管理 OpenAPI 中, 本报告不涉及)。

### V6. `views/project/characters/index.vue`

- 标题硬编码 `<ElTag>山海经动画</ElTag>` ⚠️ 与项目名称无关,**应改为动态绑定到当前项目名**。

### V7. `views/project/statistics/index.vue`

- 已并行调 5 个接口 ✓
- `firstFrameProgress` 计算为 storyboard 与 video 的平均值,**这是凭空猜的**,因为 OpenAPI 未给出"首帧图"统计接口。建议在 UI 中明确标注此值为派生指标,或者把"首帧图完成率"暂时隐藏。
- `storageTotalGB` 硬编码为 500 ⚠️,**应来自团队配额接口**。
